# MVP 기획서: 고동동 CS

> 리셀 플랫폼 고객센터 상담사를 돕는 가상 프로젝트입니다. 취업 포트폴리오용 미니 프로젝트이며, 실제 회사 이름·로고·고객 데이터는 사용하지 않습니다. 모든 문의는 직접 만든 가짜 문의입니다.

## 1. 한 줄 소개

문의가 들어오면 **종류를 자동으로 나누고, 규정 문서 근거가 붙은 답장 초안을 만들어 주는** 상담사용 사이트입니다. 고객에게 나가는 답장은 반드시 상담사가 확인합니다.

## 2. 왜 필요한가

한정판 리셀 플랫폼에는 사는 사람과 파는 사람이 모두 문의를 보냅니다. 문의 종류가 많아서 상담사는 매번 이런 일을 반복합니다.

1. 문의를 읽고 어떤 종류인지 판단한다.
2. 검수 기준, 환불 규정 같은 규정 문서를 뒤져서 관련 조항을 찾는다.
3. 조항에 맞춰 답장을 쓴다.

이 과정이 오래 걸립니다. 이 사이트는 1번과 2번, 그리고 3번의 초안까지 대신 준비해 주고, 마지막 판단은 상담사에게 맡깁니다.

## 3. 핵심 기능 (이번에 만드는 것)

### 3-1. 문의 자동 분류

문의를 아래 7가지 중 하나로 나누고, **얼마나 확실하게 나눴는지(확신도)** 를 퍼센트로 함께 보여줍니다.

| 문의한 사람 | 종류 |
|---|---|
| 구매자 | 배송 / 검수 결과 / 취소·환불 / 결제 |
| 판매자 | 검수 불합격 / 페널티 / 정산 |

분류에는 외부 서비스가 아니라 **직접 학습시킨 모델**을 사용합니다.

### 3-2. 근거가 붙은 답장 초안

- 규정 문서에서 문의와 관련된 조항을 먼저 찾습니다.
- 찾은 조항을 바탕으로 답장 초안을 만듭니다. 초안 작성에는 OpenAI API를 사용합니다.
- 초안 옆에 **어떤 조항을 근거로 썼는지** 번호와 원문을 함께 보여줍니다.
- 근거가 `[구버전]` 조항뿐이면 "구버전 기준이라 현재와 다를 수 있음" 경고를 함께 보여주고, 초안은 구버전 수치를 단정해 쓰지 않습니다.
- 모델이 말한 조항 번호가 실제 규정 문서에 있는지 프로그램이 다시 확인합니다. 없는 조항을 지어내면 걸러냅니다.

### 3-3. 위험 표현 경고

"보상해 드릴게요", "판정을 바꿔 드릴게요"처럼 상담사가 함부로 약속하면 안 되는 말이 초안에 들어 있으면 **경고를 띄우고 해당 문장을 표시**합니다. 경고 대상 문구 목록(처음에는 15~20개)은 별도 설정 화면에서 확인하고 직접 추가할 수 있습니다.

### 3-4. 상담사 승인 흐름

초안은 바로 고객에게 나가지 않습니다. 새 문의에는 모두 초안을 만들고, 초안을 만들 수 없을 때만 직접 쓰게 합니다.

| 구분 | 조건 | 처리 |
|---|---|---|
| 승인 대기 | 초안이 만들어졌다 (확신도가 낮거나 정책에 없는 내용이 있어도 만든다) | 초안을 만들어 상담사의 확인을 기다린다 |
| 직접 작성 | 초안을 만들 수 없었다(오류 등), 또는 재작성 뒤 넘겼다 | 초안 없이 상담사가 직접 쓴다 |

- 확신도가 기준값보다 낮으면 초안과 함께 "분류 확신도가 낮으니 문의 종류부터 확인하세요" 경고가 뜹니다.
- 규정 문서에 있는 내용은 규정 문서와 함께 보여주고, **조항에 없는 내용은 "규정 문서에는 없음"이라고 표시**하며 초안은 그 부분을 지어내지 않고 "확인 후 안내드리겠습니다"처럼 씁니다.

승인 대기 초안에 대해 상담사는 **승인 / 수정 / 재작성** 중 하나를 고릅니다.

- **수정:** 초안을 고치고 저장하면 바로 처리 완료되며 "수정하여 승인"으로 기록됩니다.
- **재작성:** 새 초안을 받습니다. 문의당 1번만 가능하고, 두 번째 초안에서는 재작성 대신 "직접 작성으로 넘기기"가 나타납니다.

- **다시 수정:** 처리 완료된 문의도 [다시 수정]으로 최종 답장을 고칠 수 있습니다. 상태는 처리 완료 그대로이고, 기록에는 "수정"이 새로 한 줄 쌓입니다.

기준값은 처음에 70%이며(확신도 낮음 경고를 띄우는 기준), 별도 설정 화면에서 바꿀 수 있습니다. 문의 상태는 승인 대기 / 직접 작성 / 처리 완료 세 가지입니다.

### 3-5. 작업 기록

상담사가 무엇을 했는지(승인, 수정, 재작성, 직접 작성) 누가, 언제 했는지를 기록으로 남기고 나중에 다시 볼 수 있습니다. 기록 화면에서는 상담사와 행동 종류로 거를 수 있고, 모든 상담사가 서로의 문의와 기록을 볼 수 있습니다. 상담사는 아이디와 비밀번호로 로그인하고 로그아웃 버튼으로 나올 수 있으며, 연습용 가상 상담사 계정 3개(김상담, 박상담, 이상담)를 미리 만들어 둡니다.

### 3-6. 성능 평가

정답을 미리 달아둔 연습용 문의 묶음을 한 번에 돌려서 다음을 보여줍니다.

- 전체 중 몇 개를 맞게 분류했는지
- 종류별 정확도
- 어떤 종류끼리 헷갈렸는지 (예: 취소·환불 문의를 결제 문의로 잘못 분류)
- 분류 모델은 처음부터 가장 잘하는 하나만 씁니다. 처음 버전과 고친 버전으로 나누거나 비교하지 않습니다.
- 목표 정확도 숫자는 두지 않고, 결과를 있는 그대로 보여줍니다.
- 로그인한 모든 상담사가 실행할 수 있습니다.

## 4. 화면 구성

상담사가 **한 화면에서** 아래 네 가지를 보고 버튼만 누르면 되도록 만듭니다.

```
┌───────────────┬───────────────────────────────┐
│ 문의 목록      │ 문의 내용                        │
│ (받은 문의)     ├───────────────────────────────┤
│               │ 분류 결과: 취소·환불  (확신도 92%) │
│  · 문의 1      ├───────────────────────────────┤
│  · 문의 2      │ 답장 초안                        │
│  · 문의 3      │  ⚠ 위험 표현 경고 (있을 때)       │
│               ├───────────────────────────────┤
│ [새 문의 입력]   │ 규정 문서: [RFD-03] 환불 시점 ... │
│               │ [승인]  [수정]  [재작성]          │
└───────────────┴───────────────────────────────┘
```

- 왼쪽은 미리 넣어둔 가짜 문의 목록이고, 상태 탭으로 골라 볼 수 있으며, **새 문의를 직접 입력**하거나 **CSV 파일로 여러 개를 한 번에 올려** 볼 수도 있어서 시연에 좋습니다.
- 작업 기록, 문의 현황(날짜·시간대별 문의 건수, 규정 문서에는 없음 비율, 확신도, 처리 현황), 성능 평가 결과, 설정(기준값·위험 표현 목록)은 각각 별도 화면에서 확인합니다.

## 5. 이번에 만들지 않는 것

기간이 5일이라 핵심 기능부터 만들고, 아래는 나중에 하나씩 붙입니다.

- 실제 고객 데이터 연결, 실제 메일·채팅 발송
- 회원 가입, 비밀번호 찾기 등 계정 관리 기능
- 상담사별 통계 대시보드
- 모델 자동 재학습

## 6. 사용하는 기술

| 역할 | 기술 | 쉬운 설명 |
|---|---|---|
| 화면 | React | 상담사가 보는 웹 화면 |
| 서버 | FastAPI (파이썬) | 화면의 요청을 받아 처리하는 곳 |
| 문의 분류 | scikit-learn | 직접 학습시키는 분류 모델 |
| 답장 초안 | OpenAI API | 초안 문장을 만들어 주는 외부 AI |
| 데이터 저장 | PostgreSQL (Supabase) | 문의, 초안, 작업 기록을 저장하는 클라우드 DB |

비밀번호와 API 키는 `.env` 파일에만 두고, Git에는 올라가지 않도록 `.gitignore`로 막아 두었습니다.

## 7. 데이터 준비

| 데이터 | 만드는 사람 | 용도 |
|---|---|---|
| 학습용 문의 (7개 종류, 처음 300개 + 구어체·긴 문장 보강분 241개) | Claude | 분류 모델을 가르치는 데 사용 |
| 평가용 문의 (정답 포함, 총 140개, 종류당 20개) | Gemini (프롬프트는 Claude가 작성) | 모델을 시험하는 데 사용 |
| 규정 문서 (조항 102개) | 프로젝트 작성자가 직접 수집한 공개 서비스 안내(검수기준·결제·판매·구매 FAQ)를 Claude가 이름·주소를 지우고 요약해 다시 씀 + 가상 조항 4개(사용자 검토) | 답장 근거로 사용 |

**학습용과 평가용을 서로 다른 곳에서 만드는 이유:** 같은 곳에서 만들면 말투가 비슷해서 시험 점수가 실제보다 높게 나올 수 있습니다. 평가용 데이터는 정답 표시가 맞는지 작성자가 한 번 훑어봅니다. 정답이 틀리면 모델이 억울하게 틀린 것으로 계산되기 때문입니다.

## 8. 5일 일정

| 일차 | 할 일 | 결과물 |
|---|---|---|
| 1일차 | 학습 데이터 생성, 분류 모델, 평가 도구 | 분류 정확도 |
| 2일차 | 서버 기본 구조: DB, 로그인, 분류 API | 문의를 보내면 분류가 돌아오는 서버 |
| 3일차 | 규정 문서 검색, 초안 생성, 위험 표현 경고 | 근거가 붙은 초안 |
| 4일차 | 상담사 화면: 승인·수정·재작성, 작업 기록, 설정 화면 | 한 화면에서 쓰는 사이트 |
| 5일차 | 성능 평가 화면, 전체 점검, 정리 | 성능 평가 화면과 설명 문서 |

## 9. 완성 기준

아래가 모두 되면 MVP가 완성된 것으로 봅니다.

- [ ] 문의를 넣으면 7개 종류 중 하나와 확신도가 나온다.
- [ ] 모든 문의에 초안이 만들어지고, 규정 문서 안의 내용은 규정 문서와 함께, 조항에 없는 내용은 "규정 문서에는 없음"으로 표시된다.
- [ ] 확신도가 낮은 문의는 초안과 함께 경고가 뜨고, 초안을 만들 수 없을 때만 직접 작성으로 넘어간다.
- [ ] 받은 문의를 상태 탭으로 골라 볼 수 있고 목록 너비를 조절할 수 있다.
- [ ] 위험 표현이 있으면 경고가 뜬다.
- [ ] 상담사가 승인·수정·재작성을 누르면 기록이 남고, 나중에 다시 볼 수 있다.
- [ ] 재작성은 문의당 1번만 되고, 그 뒤에도 쓰지 못하면 직접 작성으로 넘어간다.
- [ ] 처리 완료된 문의의 최종 답장을 [다시 수정]으로 고칠 수 있고, 기록이 추가된다.
- [ ] 연습용 문의 묶음을 돌리면 정확도와 헷갈린 부분이 보인다.

## 10. 알아둘 점

- 초안은 **참고용**이며, 고객에게 나가는 최종 판단은 항상 상담사가 합니다.
- 이 프로젝트의 규정 문서와 문의는 모두 가상의 내용입니다.
- 점수는 연습용 가짜 데이터 기준이라, 실제 서비스에서의 성능을 보장하지 않습니다.
