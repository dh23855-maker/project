# 개발 계획서 (plan): 고동동 CS

> [spec.md](spec.md)의 동작 설명서를 "어떤 순서로 만들 것인가"로 바꾼 계획서입니다.
> 새 기능은 넣지 않았습니다. 순서와 준비물만 정했습니다.
> 개발 기간은 5일이고, 일정의 큰 틀은 [mvp.md](mvp.md) 8장을 따릅니다.
> 각 Phase가 끝나면 **사용자 확인을 받은 뒤** 다음 Phase로 넘어갑니다.

**순서를 이렇게 한 이유**
- 분류 모델과 평가 도구가 가장 먼저 있어야 이후 모든 단계에서 "점수"로 확인할 수 있습니다.
- 서버(2~3일차)를 먼저 끝내면 화면(4일차)은 이미 동작하는 서버에 붙이기만 하면 됩니다.
- 분류 모델은 처음 버전/고친 버전으로 나누거나 비교하지 않고, 처음부터 가장 잘하는 하나만 씁니다. (Phase 3 중에 사용자가 정함. 모델 개선은 Phase 3에서 앞당겨 합니다.)

## 3. Phase 0. 준비

**목표:** 개발을 시작할 수 있는 환경을 갖춥니다.

**할 일**
1. 폴더 구조를 정합니다. (완료)
   - `backend/` : 서버, 분류 모델, 초안 만들기, 정책 검색
     - `app/` 서버 코드, `ml/` 분류 모델, `policies/` 규정 문서, `data/train/` 학습용 문의, `data/eval/` 평가용 문의, `tests/` 시험
   - `frontend/` : 상담사 화면 (Phase 4에서 만듦)
   - `database/` : 표(테이블) 설계(`schema/`)와 처음 넣을 데이터(`seed/`)
   - `docs/` : 지금까지의 문서
   - 빈 폴더는 Git이 추적하지 못해서 `.gitkeep` 빈 파일을 두었습니다. 폴더에 실제 파일이 생기면 지워도 됩니다.
2. `.env.example`을 만듭니다. 비밀값 없이 어떤 항목이 필요한지만 적습니다. (`.gitignore`는 이미 준비됨)
3. 사용자가 클라우드 DB 계정과 OpenAI API 키를 준비합니다. 값은 `.env`에만 넣습니다.
4. 필요한 도구가 컴퓨터에 있는지 확인합니다. (파이썬, Node.js)
5. 설치가 필요한 것을 정리해 **사용자에게 알린 뒤 승인받고** 설치합니다.

**Phase 시작 전에 정해야 하는 것** (spec에 없는 내용)
- ~~클라우드 DB로 Neon과 Supabase 중 무엇을 쓸지~~ → **확정:** Supabase
- ~~초안에 쓸 OpenAI 모델 이름~~ → **확정: `gpt-6-luna`** (`.env`의 `OPENAI_MODEL`). 시험 호출로 JSON 응답(조항 번호 목록)이 되는 것을 확인했습니다. 이 모델은 `temperature=0`(항상 같은 답)을 지원하지 않고, 짧은 요청에도 내부 추론 토큰이 쓰입니다. 그래서 같은 입력에도 초안이 매번 조금 다르고, 시험은 OpenAI 호출을 가짜로 대신해서 돌립니다.

**끝났다고 보는 기준**
- [x] 네 폴더에 기본 구조가 있다.
- [x] `.env.example`이 있고, 실제 `.env`는 Git에 올라가지 않는다.
- [x] DB와 API 키에 접속해 볼 수 있다. (Supabase PostgreSQL 17.11 연결 성공, OpenAI 키 확인 성공)

## 4. Phase 1. 분류 모델 첫 버전과 평가 도구 (1일차)

**목표:** 분류 모델의 첫 정확도를 숫자로 확인합니다. 이후 모델을 개선할 때의 출발점(기준 기록)입니다.

**할 일**
1. 학습용 가짜 문의 300개를 만듭니다. (7개 종류, 종류당 40~50개, 구매자·판매자 문의가 섞이게. Phase 3에서 구어체·긴 문장 등 보강분 `train_extra.csv`를 추가해 총 541개가 됨)
2. **평가용 문의를 만들 프롬프트를 작성**해서 사용자에게 드립니다. 사용자가 Gemini에 넣어 받아 옵니다. (한 번에 70개씩 두 번, 종류당 20개, 총 140개. 파일은 `backend/data/eval/eval.csv`)
   - 프롬프트에 7개 종류의 정의, 말투의 다양성, 일부러 애매한 문의 포함, 정답 표시 형식을 담습니다.
3. 사용자가 평가용 문의를 받아 오면 형식을 점검하고, 정답 표시를 사용자가 훑어봅니다.
4. 첫 모델을 만듭니다. (단어 단위로만 보는 단순 모델. 이후 Phase 3에서 개선됨)
5. 평가 도구를 만듭니다. 아래를 계산합니다.
   - 전체 정확도 ("몇 개 중 몇 개")
   - 종류별 정확도
   - 헷갈린 부분 (어떤 종류를 어떤 종류로 틀렸는지)
6. 첫 모델의 평가 결과를 저장해 둡니다. (개선 전 기준 기록. 화면에서 비교하지는 않음)

**지키는 규칙**
- 학습용 문의와 평가용 문의는 **절대 섞지 않습니다.** 평가 문의로 모델을 학습시키지 않습니다.
- 평가용 문의는 모델을 고칠 때도 학습에 쓰지 않습니다. (5일차에 "실패 사례를 보고 학습 문장을 보강"할 때는 비슷한 문장을 **새로 만들어** 학습용에 추가하고, 평가용 원문은 그대로 둡니다.)

**끝났다고 보는 기준** (spec 3장 5, 8장 5 참고)
- [x] 학습용 300개가 종류별로 40~50개씩 있다. (종류당 42~43개, 중복 0개)
- [x] 평가용 문의와 정답이 있고, 사용자가 정답을 훑어봤다. (140개, 종류당 20개. 헷갈리는 7개는 확인 후 "이대로 진행"으로 결정)
- [x] 첫 모델로 평가를 돌리면 전체·종류별 정확도와 헷갈린 부분이 나온다. (**첫 모델 정확도 84/140 = 60.0%**, 기준 기록은 `backend/ml/results/v1_eval.json`)
- [x] 평가 도구의 "몇 개 중 몇 개"가 정답 파일을 직접 센 값과 같다. (정식 평가 데이터로도 84/140 일치 확인)

## 5. Phase 2. 서버 기본 구조 (2일차)

**목표:** 로그인되고, 문의를 넣으면 분류되어 저장되는 서버를 만듭니다.

**할 일**
1. DB 표를 설계하고 만듭니다. 담아야 하는 것:
   - 상담사 (3명), 문의 (내용·상태·분류 결과·확신도), 초안 (몇 번째인지·규정 문서), 작업 기록, 위험 표현 목록, 설정(기준값), 평가 실행 결과
2. 상담사 3명(김상담, 박상담, 이상담) 계정을 미리 만들어 둡니다. (연습용 비밀번호)
3. **로그인과 로그아웃** (spec 1장)
   - 틀린 입력 안내, 빈 입력 안내, 로그인 없이는 접근 불가
4. **문의 목록 보기와 새 문의 등록** (spec 2장)
   - 빈 내용 거부, 1,000자 초과 거부
   - 미리 넣어 둘 가짜 문의 20개를 만들어 넣음 (학습용·평가용과 별도)
5. **자동 분류 연결** (spec 3장)
   - 문의가 들어오면 분류 모델이 종류와 확신도를 붙여 저장
   - 분류에 실패하면 문의는 저장함 (확정 Q3. Phase 4 뒤: 분류 없이 정책 전체에서 근거를 찾아 초안을 씀)
6. 기준값(처음 70%)을 설정으로 저장하고, 확신도가 기준값보다 낮으면 "직접 작성"으로 보내는 규칙을 연결합니다. (근거 조건은 Phase 3에서 붙음. **Phase 4 뒤 변경:** 낮아도 초안을 만들고 경고만 띄움)

**끝났다고 보는 기준** (spec 1장 5, 2장 5, 3장 5)
- [x] 3개 계정으로 각각 로그인된다. 틀린 비밀번호와 빈 입력이 안내와 함께 막힌다. (아이디 kim / park / lee)
- [x] 로그인 없이는 문의 목록을 볼 수 없다.
- [x] 미리 넣은 문의 20개가 목록으로 나온다. (당시 승인 대기 6개, 직접 작성 14개)
- [x] 새 문의를 등록하면 저장되고 종류와 확신도가 붙는다. 빈 내용·1,000자 초과는 막힌다.
- [x] 다른 상담사로 로그인해도 같은 문의가 보인다.

**Phase 2에서 알아둘 점**
- 이 단계의 "승인 대기"는 확신도가 기준값 이상이라는 뜻일 뿐, 아직 초안이 붙어 있지 않습니다. 초안과 근거 조건은 Phase 3에서 붙고, 이미 들어 있는 "승인 대기" 문의에도 그때 초안을 만들어 붙입니다.
- 첫 모델의 한계로 미리 넣은 문의 20개 중 14개가 "직접 작성"으로 갔습니다. 모델을 개선하면(Phase 3) 미리 넣은 문의를 다시 넣어 상태를 새로 잡습니다.
- DB는 Supabase `public` 영역에 표 7개(+변경 이력 1개)를 만들었고, 모두 접근 제한(RLS)을 켰습니다. 시험은 임시 영역에서만 돌립니다.

## 6. Phase 3. 정책 근거와 답장 초안 (3일차)

**목표:** 근거가 붙은 초안이 만들어지고, 위험 표현이 잡히고, 승인 흐름의 규칙이 서버에서 동작합니다.

**할 일**
1. **규정 문서 읽기와 조항 나누기** (spec 4장)
   - `policy_clauses.md`를 `### [ID] 제목 [라벨]` 단위로 나누어 저장. `응대 주의:` 줄은 내부 지침으로 따로 분리 (고객에게 인용하지 않음)
2. **관련 조항 검색**
   - 분류된 문의 종류에 연결된 조항(규정 문서의 매핑표)으로 후보를 좁힘
   - 그 안에서 문의와 비슷한 조항을 최대 3개 후보로 뽑음 (낮은 유사도 기준 0.06: 확실히 상관없는 조항만 걸러냄)
   - 초안을 쓰는 모델이 실제로 쓴 조항과 조항에 없는 내용을 말함 (글자 유사도만으로는 엉뚱한 조항에 걸린 문의를 가르기 어려워서 모델의 판단을 한 겹 더함). *Phase 4 뒤 변경: 예전에는 "답할 수 없다"고 하면 직접 작성으로 보냈지만, 지금은 "규정 문서에는 없음"으로 표시하고 초안은 씀*
   - 후보가 하나도 없어도 초안을 씀 ("규정 문서에는 없음")
   - 유사도 기준값은 학습용·미리 넣은 문의와 정책에 없는 질문으로 정했고, **평가용 문의는 쓰지 않음**
3. **초안 만들기 (OpenAI)**
   - 문의와 후보 조항을 넘겨 초안과 규정 문서 번호를 받음
   - 초안 스타일(확정): 정중한 존댓말, 4~7문장, 인사와 마무리 포함. 약속 금지 표현과 정책에 없는 내용은 쓰지 않도록 지시. 조항의 `응대 주의:` 줄은 지침으로만 쓰고 고객에게 인용하지 않음
   - 근거가 `[구버전]`(또는 `[구버전 포함]`) 조항뿐이면 "구버전 기준" 표시를 함께 돌려주고, 초안에는 구버전 수치를 단정해 쓰지 않도록 지시
   - 실패하면 "직접 작성"으로 보냄 (확정 Q3)
4. **규정 문서 번호 검증**
   - 초안이 말한 번호가 규정 문서에 실제로 있는지 확인
   - 없는 번호가 하나라도 있으면 그 초안은 쓰지 않고 "직접 작성"으로 보냄 (확정 Q4)
5. **위험 표현 경고** (spec 5장)
   - 처음 목록 15~20개를 제가 만들고 사용자가 검토해 확정
   - 초안, 수정해서 저장하는 글, 직접 쓴 답장을 검사하되 저장은 막지 않음 (확정 Q2)
   - 경고에 해당 문장을 함께 돌려줌
   - 새 위험 표현 추가 (빈 문구는 거부)
6. **승인 흐름의 규칙** (spec 6장). 화면 없이 서버에서 먼저 동작하게 합니다.
   - 갈래: 초안이 만들어지면 승인 대기 / 초안을 못 만들면 직접 작성 (*Phase 4 뒤 변경: 예전에는 확신도 ≥ 기준값이고 근거 있음일 때만 승인 대기*)
   - [승인]: 처리 완료, 기록에 "승인"
   - [수정]: 빈 내용 거부, 저장하면 처리 완료, 기록에 "수정하여 승인" + 초안·최종 답장
   - [재작성]: 문의당 1번, 새 초안 만들기. 실패하면 첫 초안 유지(횟수 안 셈). 기록에 첫 초안·새 초안
   - [직접 작성으로 넘기기]: 두 번째 초안에서 상태를 직접 작성으로
   - [직접 작성 등록]: 빈 내용 거부, 처리 완료, 기록에 "직접 작성"
   - [다시 수정]: 처리 완료 문의의 최종 답장 변경, 기록 한 줄 추가
   - 동시 처리: 먼저 저장한 사람만 적용, 나중 사람에게 안내 (확정 Q7)
7. **기준값 변경** (50~95% 범위, 저장 후 새 문의부터 적용) (확정 Q5)
8. **작업 기록 쌓기와 불러오기**: 시간·상담사·문의·행동·초안·최종 답장, 상담사와 행동으로 거르기

**끝났다고 보는 기준** (spec 4장 5, 5장 5, 6장 각 5, 7장 5)
- [x] 정책에 답이 있는 문의에 초안과 규정 문서가 붙는다. 근거 번호·원문이 규정 문서와 같다. (실제 `gpt-6-luna`로 확인, 시험으로 원문 일치 확인)
- [x] 정책에 없는 문의는 엉뚱한 초안이 나오지 않는다. (당시: 직접 작성으로 보냄, 정책에 없는 질문 15개 중 엉뚱한 초안 0개. Phase 4 뒤: 초안은 쓰되 "규정 문서에는 없음" 표시)
- [x] 없는 조항 번호(또는 제공하지 않은 조항 번호)를 말하는 초안(시험용)은 걸러져 직접 작성으로 간다.
- [x] 위험 표현이 들어간 글에서 경고와 문장이 나오고, 저장은 막히지 않는다.
- [x] 승인, 수정, 재작성(1번), 직접 작성, 다시 수정이 각각 규칙대로 동작하고 기록이 남는다.
- [x] 두 사람이 동시에 같은 문의를 처리하면 먼저 한 사람만 적용된다.
- [x] 기준값을 바꾸면 새 문의부터 적용되고, 범위를 벗어난 값은 거부된다.

**Phase 3에서 바뀌거나 새로 알게 된 것**
- 분류 모델을 처음부터 가장 잘하는 하나로 정했습니다 (처음 버전/고친 버전 비교 취소). 글자 조각 방식 + 보강 문장 241개 → 평가용 140개 중 **106개 맞힘(75.7%)**. 첫 모델은 84개(60.0%)였습니다. 보강 전에 평가용 문의를 읽었기 때문에 이 점수는 낙관적일 수 있습니다.
- 근거 찾기는 유사도 기준(0.06) + 모델의 "답할 수 있는가" 판단 두 겹입니다.
- 미리 넣은 가짜 문의 20개는 새 모델·정책으로 다시 넣어 **승인 대기 7개, 직접 작성 13개**가 되었습니다. (Phase 4 뒤 규칙 변경으로 실제 DB에 다시 넣어 전부 초안이 붙은 승인 대기가 되었습니다. 직접 써 본 2건(#46 재작성, #59 승인)과 작업 기록은 그대로 두었습니다.)
- 시험은 총 127개이며 OpenAI 호출은 가짜로 대신해 비용이 들지 않습니다.

- **문의 현황**(메뉴 "문의 현황", `/stats`): 서버 `GET /api/stats/inquiries?days=7|14|30`(한국 시간 날짜별 × 종류별 건수, 문의 없는 날 0건), 화면은 요약 4개 + 쌓은 막대 그래프(종류별 고정 색, 마우스·키보드 말풍선) + 종류별 합계 + 표로 보기. 색은 검증된 8색 팔레트(`validate_palette`로 인접 색 CVD·밝기 구분 통과, 대비 경고는 표·값 표시로 보완)의 앞 7칸 + 분류 없음 회색.
- 시험: 서버 183개(문의 현황 10개 추가), 화면 106개. 한국 시간·기간 경계를 일부러 틀리게 해 보는 점검을 시험이 잡아냄.
- **통계 확장(추천 1~3번 + 오늘 탭):** 서버 응답을 날짜별(`daily`) 대신 칸별(`buckets`, 오늘이면 시간대별)로 바꾸고, 규정 문서에는 없음 비율·확신도가 낮은 문의 비율·처리 현황(상태, 마지막 처리 방법, 초안 그대로 승인 비율, 재작성 비율, 처리 시간 중앙값·평균)을 추가. 기간 `days=1`이 오늘. 서버 시험 25개(오늘, 규정 없음 최신 초안 기준, 확신도 기준값 경계, 처리 방법, 처리 시간 등), 화면 시험 추가.
- **화면 수정 3차:** ① 처리 버튼이 글씨를 덮던 것을 "버튼 자리가 화면 밖일 때만 내용 칸 아래에 나타남"으로 고침 ② "고동동 CS"를 누르면 상담 화면으로 ③ 메뉴 선택 표시가 부드럽게 미끄러져 이동 ④ 초안을 문단으로 나눠 쓰도록 지침 변경과 줄바꿈 정리(`tidy_paragraphs`).
- - **CSV로 문의 여러 개 올리기:** 서버 변경 없이 화면이 문의를 하나씩 차례로 등록(`frontend/src/csv.js`, `components/BatchUpload.jsx`). 한 번에 30개·1,000자·1MB, 진행 상황 표시, 일부 실패는 건너뛰고 계속(연결 끊김·로그인 풀림만 멈춤), 중단 버튼, 실패 목록, EUC-KR 엑셀 CSV 지원. 화면 시험 26개 추가(총 153개), 일부러 코드를 틀리게 해 보는 점검 5가지를 모두 시험이 잡아냄. 실제 서버·OpenAI로 3줄 파일 확인 후 시험 문의 2개는 삭제.
- **작업 기록 정리:** 머리글 "행동"을 뱃지와 같은 위치로 맞추고, [자세히]의 초안·새 초안·최종 답장을 각각 둥근 상자(새 초안 보라, 최종 답장 초록)로 구분. 화면 시험 2개 추가.
- 시험: 서버 195개, 화면 125개. 일부러 코드를 틀리게 해 보는 점검(초안 순서, 처리 방법 순서, 기준값 경계, 공백 메모, 한국 시간, 기간 경계)을 시험이 잡아냄.
- 알아 둘 점: DB에 있는 예전 초안(규정 문서 보강 전)은 "규정 문서에는 없음" 비율이 높게(약 78%) 나옴. 새 규정으로 초안을 다시 만들면 달라질 것.
- 개발 편의: `API_TARGET` 환경변수로 화면 서버가 다른 주소의 서버를 바라보게 할 수 있음(새 서버를 켜서 시험할 때만 사용).

**규정 문서 보강 (Phase 5 뒤, 사용자 요청)**
- 목표: 초안을 쓸 때 참고할 규정을 풍부하게 해서 "직접 작성"과 "규정 문서에는 없음"을 줄이고 초안의 정확도를 높입니다. 순서: ① 규정 문서 보강 → ② 정답 표 만들기 → ③ 찾는 방식 3가지(TF-IDF / 임베딩 / 섞기)를 같은 정답 표로 비교해 가장 좋은 것으로 교체.
- ① 완료: 사용자가 직접 수집한 검수기준·결제·판매·구매 FAQ를 바탕으로 `policy_clauses.md`를 102개 조항으로 새로 씀. 업체명·주소·전화번호·브랜드명 제거, 기존 47개 ID는 유지. 가상 조항은 4개로 줄어들고(수치는 대부분 공개 서비스 안내 기준), 구버전은 SNK-08(냄새) 하나만 남음.
- 새 형식: 조항마다 `- 이런 문의에 쓰임:` 줄(고객 말투 예시, `/`로 구분)을 두어 규정 문서를 찾을 때만 씀. 화면과 초안 재료에는 나오지 않음. 새 영역: BAG(가방·시계), TEC(테크 등), GLD(금·은), INT(해외배송), SEL(판매 절차), TKT(제휴 티켓).
- 초안 지침에 규칙 3개 추가: 해당 조항을 모두 반영하고 이용 경로·수치는 구체적으로 안내 / 공감 → 결론 → 규정 안내 → 다음 행동 → 마무리 순서 / 필요한 정보가 없으면 요청.
- 용어 변경: 화면·문서·서버 메시지의 "근거 조항"을 "규정 문서"로 바꿈 (조항 ID와 코드 이름은 그대로).
- 시험: 서버 148개 통과. 새 형식을 읽지 못하게 만들어 보는 점검도 시험이 잡아냄.
- ② 완료: `backend/data/eval/retrieval_gold.csv` — 평가용 문의 140개에 정답 조항을 붙임(충분히 답함 90 / 일부만 답함 44 / 규정 없음 6). 읽기·점검 코드는 `ml/retrieval_data.py`, 시험 10개(형식 오류, 없는 조항 번호, none 규칙, 평가용 문의와의 일치). **주의: 정답 표는 Claude가 만들었고, 조항의 "이런 문의에 쓰임" 예시 일부가 평가용 문의 말투를 따라 쓰였을 수 있어 예시 줄을 넣은 점수는 낙관적일 수 있음.** 그래서 비교는 예시 줄 포함/제외 두 가지로 재고, 가능하면 새 문의(다른 생성형 AI가 작성)로 한 번 더 확인함.
- ③ 완료: 같은 정답 표(정답이 있는 134개)로 세 방식을 비교하고 **임베딩(`text-embedding-3-large`)으로 교체**. 비교 코드는 `ml/retrieval_compare.py`(`python -m ml.retrieval_compare [모델]`), 결과는 `ml/results/retrieval_compare_<모델>.json`. 섞는 비율(TF-IDF 0.5)은 결과를 보기 전에 정해 둠.

| 3등 안 정확도 (분류가 맞을 때 / 정책 전체에서) | TF-IDF | 임베딩 small | 섞기 small | **임베딩 large** | 섞기 large |
|---|---|---|---|---|---|
| 예시 줄 포함 | 79.1% / 66.4% | 75.4% / 61.2% | 82.1% / 74.6% | **88.1% / 76.9%** | 84.3% / 74.6% |
| 예시 줄 제외 | 66.4% / 49.3% | 67.9% / 53.7% | 70.9% / 54.5% | **81.3% / 70.1%** | 76.9% / 62.7% |

  - 임베딩 large가 네 조건 모두에서 TF-IDF보다 9~21%p 높음(예시 줄 없이도 81.3%). 임베딩 small은 TF-IDF와 비슷하거나 낮았고, 섞기는 large에서는 임베딩 단독보다 낮았음.
  - 1등 안: 66.4%(분류가 맞을 때, 예시 포함), 58.2%(예시 제외). TF-IDF는 59.0% / 40.3%.
  - 서버에는 이 기준(개선 2%p 이상이면 교체)대로 임베딩 large를 적용. 서버 경로(`find_evidence` 상위 3개)로 다시 잰 값이 비교 결과와 같음(88.1% / 66.4%). 문의 하나당 약 0.17초.
  - 실패해도 멈추지 않음: 조항 벡터를 못 만들거나 문의 임베딩이 실패하면 그 순간만 TF-IDF로 찾음. OpenAI 키가 없어도 TF-IDF로 동작.
  - 임베딩 점수 기준은 0.24(정답 조항 점수 하위 5%가 0.29, 엉뚱한 문장은 0.23 이하). 확실히 상관없는 것만 거르고 "실제로 쓸지"는 모델이 판단하는 기존 방식 유지.
  - 조항 벡터는 `backend/policies/embedding_cache.json`에 저장(Git 제외, 다시 만들 수 있음, 약 6MB). 고객 문의 벡터는 저장하지 않음.
  - 한계: 정답 표가 Claude 작성이고 평가용 문의 140개에 맞춰 예시 줄을 썼기 때문에 예시 줄 포함 점수는 낙관적일 수 있음. 예시 줄 제외 점수(81.3%)가 더 보수적. 새 문의로 한 번 더 확인하는 것이 좋음.
- 지금 TF-IDF 기준선(정답이 있는 134개, 분류가 맞다고 가정): 예시 줄 포함 1등 안 59.0% / 3등 안 79.1%, 예시 줄 제외 40.3% / 66.4%. 정책 전체에서 찾으면(확신도가 낮을 때) 포함 44.8% / 66.4%, 제외 26.9% / 49.3%.

## 11. 작업 규칙

- Phase를 하나 마칠 때마다 사용자에게 GitHub에 커밋하고 푸시할지 물어봅니다. 사용자가 승인하면 그때 커밋과 푸시를 합니다. 묻기 전에는 커밋하거나 푸시하지 않습니다.
- 커밋에는 해당 Phase의 파일만 담고, 비밀값이 든 파일(`.env` 등)은 포함하지 않습니다.
- 설치와 외부 서비스 연결은 사용자에게 알리고 승인받은 뒤 진행합니다.
- 비밀값(API 키, DB 주소, 비밀번호)은 `.env`에만 두고 문서와 코드에 쓰지 않습니다.
- 결정이 바뀌면 [mvp.md](mvp.md), [PRD.md](PRD.md), [spec.md](spec.md), 이 문서를 모두 함께 고칩니다.
- 모든 문의는 가짜 문의입니다. 실제 고객 데이터와 실제 회사 이름·로고는 쓰지 않습니다.
