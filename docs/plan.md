# 개발 계획서 (plan): 상담사 답변 도우미

> [spec.md](spec.md)의 동작 설명서를 "어떤 순서로 만들 것인가"로 바꾼 계획서입니다.
> 새 기능은 넣지 않았습니다. 순서와 준비물만 정했습니다.
> 개발 기간은 5일이고, 일정의 큰 틀은 [mvp.md](mvp.md) 8장을 따릅니다.
> 각 Phase가 끝나면 **사용자 확인을 받은 뒤** 다음 Phase로 넘어갑니다.

## 2. 사용자가 준비해야 하는 것

| 준비물 | 필요한 시점 | 설명 |
|---|---|---|
| OpenAI API 키 | Phase 3 시작 전 (Phase 0에 받아 두면 좋음) | 초안 작성에 사용. `.env`에만 넣고 Git에는 올리지 않음 |
| 클라우드 DB 계정 (Neon 또는 Supabase 중 하나) | Phase 2 시작 전 (Phase 0에 만들어 두면 좋음) | 접속 주소를 `.env`에 넣음 |
| 정책 문서 텍스트 (검수기준, 환불규정 등) | Phase 3 시작 전 | 문서별 파일, 안에 조항 번호. 표기 규칙은 받을 때 안내 |
| 평가용 문의 묶음 (정답 포함) | Phase 1 마지막 | 다른 생성형 AI가 만듦. 만드는 프롬프트는 제가 Phase 1에서 작성 |
| 위험 표현 목록 검토 | Phase 3 | 제가 15~20개 초안을 만들면 사용자가 빼고 더해서 확정 |
| 평가용 문의의 정답 표시 훑어보기 | Phase 1 마지막 | 정답이 틀리면 모델이 억울하게 틀린 것으로 계산됨 |

## 3. Phase 0. 준비

**목표:** 개발을 시작할 수 있는 환경을 갖춥니다.

**할 일**
1. 폴더 구조를 정합니다. (제안)
   - `backend/` : 서버, 분류 모델, 초안 만들기, 정책 검색
   - `frontend/` : 상담사 화면
   - `database/` : 표(테이블) 설계와 처음 넣을 데이터
   - `docs/` : 지금까지의 문서
2. `.env.example`을 만듭니다. 비밀값 없이 어떤 항목이 필요한지만 적습니다. (`.gitignore`는 이미 준비됨)
3. 사용자가 클라우드 DB 계정과 OpenAI API 키를 준비합니다. 값은 `.env`에만 넣습니다.
4. 필요한 도구가 컴퓨터에 있는지 확인합니다. (파이썬, Node.js)
5. 설치가 필요한 것을 정리해 **사용자에게 알린 뒤 승인받고** 설치합니다.

**Phase 시작 전에 정해야 하는 것** (spec에 없는 내용)
- 클라우드 DB로 Neon과 Supabase 중 무엇을 쓸지
- 초안에 쓸 OpenAI 모델 이름

**끝났다고 보는 기준**
- [ ] 네 폴더에 기본 구조가 있다.
- [ ] `.env.example`이 있고, 실제 `.env`는 Git에 올라가지 않는다.
- [ ] DB와 API 키에 접속해 볼 수 있다.

## 4. Phase 1. 분류 모델 첫 버전과 평가 도구 (1일차)

**목표:** 처음 버전의 정확도를 숫자로 확인합니다. 이 숫자가 5일차 비교의 출발점입니다.

**할 일**
1. 학습용 가짜 문의 300개를 만듭니다. (7개 종류, 종류당 40~50개, 구매자·판매자 문의가 섞이게)
2. **평가용 문의를 만들 프롬프트를 작성**해서 사용자에게 드립니다. 사용자가 다른 생성형 AI에 넣어 받아 옵니다.
   - 프롬프트에 7개 종류의 정의, 말투의 다양성, 일부러 애매한 문의 포함, 정답 표시 형식을 담습니다.
3. 사용자가 평가용 문의를 받아 오면 형식을 점검하고, 정답 표시를 사용자가 훑어봅니다.
4. 처음 버전 모델을 만듭니다. (단어 단위로만 보는 단순 모델)
5. 평가 도구를 만듭니다. 아래를 계산합니다.
   - 전체 정확도 ("몇 개 중 몇 개")
   - 종류별 정확도
   - 헷갈린 부분 (어떤 종류를 어떤 종류로 틀렸는지)
6. 처음 버전의 평가 결과를 저장해 둡니다. (5일차 비교용)

**지키는 규칙**
- 학습용 문의와 평가용 문의는 **절대 섞지 않습니다.** 평가 문의로 모델을 학습시키지 않습니다.
- 평가용 문의는 모델을 고칠 때도 학습에 쓰지 않습니다. (5일차에 "실패 사례를 보고 학습 문장을 보강"할 때는 비슷한 문장을 **새로 만들어** 학습용에 추가하고, 평가용 원문은 그대로 둡니다.)

**끝났다고 보는 기준** (spec 3장 5, 8장 5 참고)
- [ ] 학습용 300개가 종류별로 40~50개씩 있다.
- [ ] 평가용 문의와 정답이 있고, 사용자가 정답을 훑어봤다.
- [ ] 처음 버전으로 평가를 돌리면 전체·종류별 정확도와 헷갈린 부분이 나온다.
- [ ] 평가 도구의 "몇 개 중 몇 개"가 정답 파일을 직접 센 값과 같다.

## 5. Phase 2. 서버 기본 구조 (2일차)

**목표:** 로그인되고, 문의를 넣으면 분류되어 저장되는 서버를 만듭니다.

**할 일**
1. DB 표를 설계하고 만듭니다. 담아야 하는 것:
   - 상담사 (3명), 문의 (내용·상태·분류 결과·확신도), 초안 (몇 번째인지·근거 조항), 작업 기록, 위험 표현 목록, 설정(기준값), 평가 실행 결과
2. 상담사 3명(김상담, 박상담, 이상담) 계정을 미리 만들어 둡니다. (연습용 비밀번호)
3. **로그인과 로그아웃** (spec 1장)
   - 틀린 입력 안내, 빈 입력 안내, 로그인 없이는 접근 불가
4. **문의 목록 보기와 새 문의 등록** (spec 2장)
   - 빈 내용 거부, 1,000자 초과 거부
   - 미리 넣어 둘 가짜 문의 20개를 만들어 넣음 (학습용·평가용과 별도)
5. **자동 분류 연결** (spec 3장)
   - 문의가 들어오면 분류 모델이 종류와 확신도를 붙여 저장
   - 분류에 실패하면 문의는 저장하고 "직접 작성"으로 보냄 (확정 Q3)
6. 기준값(처음 70%)을 설정으로 저장하고, 확신도가 기준값보다 낮으면 "직접 작성"으로 보내는 규칙을 연결합니다. (근거 조건은 Phase 3에서 붙음)

**끝났다고 보는 기준** (spec 1장 5, 2장 5, 3장 5)
- [ ] 3개 계정으로 각각 로그인된다. 틀린 비밀번호와 빈 입력이 안내와 함께 막힌다.
- [ ] 로그인 없이는 문의 목록을 볼 수 없다.
- [ ] 미리 넣은 문의 20개가 목록으로 나온다.
- [ ] 새 문의를 등록하면 저장되고 종류와 확신도가 붙는다. 빈 내용·1,000자 초과는 막힌다.
- [ ] 다른 상담사로 로그인해도 같은 문의가 보인다.

## 6. Phase 3. 정책 근거와 답장 초안 (3일차)

**목표:** 근거가 붙은 초안이 만들어지고, 위험 표현이 잡히고, 승인 흐름의 규칙이 서버에서 동작합니다.

**할 일**
1. **정책 문서 읽기와 조항 나누기** (spec 4장)
   - 사용자가 준 문서를 조항 번호 단위로 나누어 저장
2. **관련 조항 검색**
   - 문의와 관련된 조항을 찾아 최대 3개까지 후보로 뽑음
   - 하나도 없으면 "근거 없음" → 직접 작성
3. **초안 만들기 (OpenAI)**
   - 문의와 후보 조항을 넘겨 초안과 근거 조항 번호를 받음
   - 실패하면 "직접 작성"으로 보냄 (확정 Q3)
4. **근거 조항 번호 검증**
   - 초안이 말한 번호가 정책 문서에 실제로 있는지 확인
   - 없는 번호가 하나라도 있으면 그 초안은 쓰지 않고 "직접 작성"으로 보냄 (확정 Q4)
5. **위험 표현 경고** (spec 5장)
   - 처음 목록 15~20개를 제가 만들고 사용자가 검토해 확정
   - 초안, 수정해서 저장하는 글, 직접 쓴 답장을 검사하되 저장은 막지 않음 (확정 Q2)
   - 경고에 해당 문장을 함께 돌려줌
   - 새 위험 표현 추가 (빈 문구는 거부)
6. **승인 흐름의 규칙** (spec 6장). 화면 없이 서버에서 먼저 동작하게 합니다.
   - 갈래: 확신도 ≥ 기준값이고 근거 있음 → 승인 대기 / 아니면 직접 작성
   - [승인]: 처리 완료, 기록에 "승인"
   - [수정]: 빈 내용 거부, 저장하면 처리 완료, 기록에 "수정하여 승인" + 초안·최종 답장
   - [재작성]: 문의당 1번, 새 초안 만들기. 실패하면 첫 초안 유지(횟수 안 셈). 기록에 첫 초안·새 초안
   - [직접 작성으로 넘기기]: 두 번째 초안에서 상태를 직접 작성으로
   - [직접 작성 등록]: 빈 내용 거부, 처리 완료, 기록에 "직접 작성"
   - [다시 수정]: 처리 완료 문의의 최종 답장 변경, 기록 한 줄 추가
   - 동시 처리: 먼저 저장한 사람만 적용, 나중 사람에게 안내 (확정 Q7)
7. **기준값 변경** (50~95% 범위, 저장 후 새 문의부터 적용) (확정 Q5)
8. **작업 기록 쌓기와 불러오기**: 시간·상담사·문의·행동·초안·최종 답장, 상담사와 행동으로 거르기

**끝났다고 보는 기준** (spec 4장 5, 5장 5, 6장 각 5, 7장 5)
- [ ] 정책에 답이 있는 문의에 초안과 근거 조항이 붙는다. 근거 번호·원문이 정책 문서와 같다.
- [ ] 정책에 없는 문의는 초안 없이 직접 작성으로 간다.
- [ ] 없는 조항 번호를 말하는 초안(시험용)은 걸러져 직접 작성으로 간다.
- [ ] 위험 표현이 들어간 글에서 경고와 문장이 나오고, 저장은 막히지 않는다.
- [ ] 승인, 수정, 재작성(1번), 직접 작성, 다시 수정이 각각 규칙대로 동작하고 기록이 남는다.
- [ ] 두 사람이 동시에 같은 문의를 처리하면 먼저 한 사람만 적용된다.
- [ ] 기준값을 바꾸면 새 문의부터 적용되고, 범위를 벗어난 값은 거부된다.

## 7. Phase 4. 상담사 화면 (4일차)

**목표:** 상담사가 한 화면에서 문의·분류 결과·초안·근거를 보고 버튼만 눌러 처리합니다.

**할 일** (화면 5개, spec 9장)
1. **로그인 화면**: 아이디·비밀번호, 실패 안내
2. **상담 화면 (메인)**: 왼쪽 문의 목록(상태 표시)과 새 문의 입력, 오른쪽 문의 내용 / 분류 결과와 확신도 / 답장 초안과 위험 표현 경고 / 근거 조항 번호·원문 / 버튼
   - 승인 대기: [승인] [수정] [재작성]
   - 재작성 후 두 번째 초안: [승인] [수정] [직접 작성으로 넘기기]
   - 직접 작성: 답장 쓰는 칸과 [등록]
   - 처리 완료: 최종 답장과 [다시 수정]
   - 모든 화면 위에 로그인한 상담사 이름과 [로그아웃]
   - 다른 상담사가 먼저 처리했을 때의 안내
3. **작업 기록 화면**: 목록, 상담사·행동 필터, 없을 때 안내
4. **설정 화면**: 기준값 변경(50~95%), 위험 표현 목록 보기와 추가
5. **화면 이동**: 로그인 → 상담 화면, 로그인 없이는 다른 화면 접근 불가

**끝났다고 보는 기준** (spec 1~7장의 화면 관련 확인 항목)
- [ ] 상담 화면 한 곳에서 문의·분류·초안·근거·버튼이 모두 보인다.
- [ ] 상담사가 버튼만 눌러 승인, 수정, 재작성, 직접 작성, 다시 수정을 끝낼 수 있다.
- [ ] 위험 표현 경고에 해당 문장이 표시된다.
- [ ] 작업 기록 화면에서 필터가 동작한다.
- [ ] 설정 화면에서 기준값과 위험 표현을 바꿀 수 있고 잘못된 값은 안내가 나온다.
- [ ] 3개 계정으로 로그인해 서로의 문의와 기록이 보인다.

## 8. Phase 5. 고친 버전·평가 화면·마무리 (5일차)

**목표:** 처음 버전과 고친 버전의 비교를 보여주고, 전체를 점검합니다.

**할 일**
1. **처음 버전의 실패 사례 분석**: Phase 1 결과에서 틀린 문의와 헷갈린 종류쌍을 확인합니다.
2. **고친 버전 모델 만들기**
   - 글자 조각 방식으로 바꿈
   - 실패 사례를 보고 비슷한 학습 문장을 **새로 만들어** 학습용에 보강 (평가용 원문은 학습에 쓰지 않음)
   - 무엇을 고쳤는지 기록해 둠 (화면 설명에 사용)
3. **평가 실행 기능** (spec 8장)
   - [평가 실행] 한 번으로 두 버전을 함께 돌림
   - 결과(전체·종류별 정확도·헷갈린 부분)를 실행마다 저장, 오류 시 반쪽 결과는 저장하지 않음
   - 평가 문의는 상담 목록에 섞이지 않음
4. **성능 평가 화면**: 전체 정확도, 종류별 정확도, 헷갈린 부분, 두 버전 나란히 비교(오른 폭과 고친 내용), 이전 실행 결과 보기
5. **전체 점검**: spec 11장 첫 버전 완성 확인표를 처음부터 끝까지 확인
6. **정리**: 사용법(README), 포트폴리오 설명용 정리

**끝났다고 보는 기준** (spec 8장 5, 11장)
- [ ] [평가 실행] 한 번에 끝까지 돌고, "몇 개 중 몇 개"가 정답 파일을 센 값과 같다.
- [ ] 두 버전이 나란히 보이고 정확도 차이와 고친 내용이 적혀 있다.
- [ ] 평가를 두 번 실행해도 이전 결과를 다시 볼 수 있다.
- [ ] 평가 문의가 상담 목록에 섞이지 않는다.
- [ ] spec 11장의 완성 기준이 모두 통과한다.

## 9. 일정이 밀릴 때

범위는 줄이지 않고 **만드는 순서만** 조절합니다. 아래 순서로 마지막에 만듭니다. 5일 안에 못 끝날 경우 사용자와 상의해 정합니다.

1. 이전 평가 실행 결과 다시 보기 (spec 8장)
2. 동시 처리 안내 (spec Q7)
3. 작업 기록 필터 (spec 7장)
4. [다시 수정] (spec 6-7)

그 이전 항목(로그인, 분류, 초안과 근거, 위험 표현, 승인·수정·재작성·직접 작성, 기록, 두 버전 비교)은 첫 버전에서 빠지면 안 되는 핵심입니다.

## 10. 위험 요소와 대비

| 위험 | 대비 |
|---|---|
| 평가 데이터가 늦게 오거나 정답이 틀림 | Phase 1에서 프롬프트를 먼저 드리고, 정답을 훑어보는 시간을 둠 |
| 학습 데이터가 적어 정확도가 낮음 | 낮으면 낮은 대로 처음 버전으로 기록. 5일차에 보강 후 비교 (목표 숫자는 두지 않음) |
| OpenAI 응답이 느리거나 실패 | 실패 시 직접 작성으로 넘기는 규칙을 Phase 3에 포함 |
| 초안이 정책에 없는 말을 지어냄 | 조항 번호 검증과 위험 표현 검사 |
| 정책 문서가 늦게 옴 | Phase 3 전에 받아야 함. 늦으면 3일차가 밀리므로 Phase 0에서 일정 확인 |
| 클라우드 DB·API 키 설정 지연 | Phase 0에서 미리 접속 확인 |

## 11. 작업 규칙

- Git 초기화와 커밋은 사용자가 요청할 때만 합니다.
- 설치와 외부 서비스 연결은 사용자에게 알리고 승인받은 뒤 진행합니다.
- 비밀값(API 키, DB 주소, 비밀번호)은 `.env`에만 두고 문서와 코드에 쓰지 않습니다.
- 결정이 바뀌면 [mvp.md](mvp.md), [PRD.md](PRD.md), [spec.md](spec.md), 이 문서를 모두 함께 고칩니다.
- 모든 문의는 가짜 문의입니다. 실제 고객 데이터와 실제 회사 이름·로고는 쓰지 않습니다.
