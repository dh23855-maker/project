# 동작 설명서 (spec): CSFlow

> [PRD.md](PRD.md)에서 정한 기능이 "실제로 어떻게 동작해야 하는가"를 사용자의 행동과 결과 중심으로 정리한 문서입니다.
> PRD에서 정한 조건은 그대로 따랐고, 새 기능은 넣지 않았습니다.
> PRD만으로 정할 수 없던 내용은 **확인 필요**(Q1~Q12)로 표시해 하나씩 물어서 모두 정했습니다. 본문의 "(확정: Q번호)"는 12장 표와 같습니다. 지금 남은 확인 필요 항목은 없습니다.
> 모든 문의는 직접 만든 가짜 문의이며, 승인된 답장은 고객에게 실제로 보내지지 않습니다.

## 0. 먼저 알아둘 것

### 0-1. 사용하는 말

| 말 | 뜻 |
|---|---|
| 상담사 | 사이트를 쓰는 사람. 김상담, 박상담, 이상담 3명이 있습니다. |
| 확신도 | 문의를 7가지 종류 중 하나로 나눈 결과를 얼마나 믿을 수 있는지 나타내는 %입니다. |
| 기준값 | 확신도가 이 값보다 낮으면 "분류 확신도가 낮음" 경고를 초안과 함께 보여줍니다. 낮아도 초안은 만듭니다. 처음 값은 70%입니다. |
| 규정 문서 | 초안을 쓸 때 바탕으로 한 규정 문서의 조항입니다. (예: "[PEN-04] 가품·사용감") 초안이 규정 문서를 하나도 참고하지 못했을 때는 "규정 문서에는 없음"이라고 표시합니다. |
| 위험 표현 | "보상해 드릴게요"처럼 상담사가 함부로 약속하면 안 되는 말입니다. |

### 0-2. 문의의 상태 (3가지)

| 상태 | 뜻 |
|---|---|
| 승인 대기 | 초안이 만들어졌고 상담사가 승인·수정·재작성을 고르기를 기다립니다. 새 문의는 거의 모두 이 상태로 시작합니다. |
| 직접 작성 | 초안을 만들 수 없었거나(외부 서비스 오류 등), 상담사가 재작성 뒤 [직접 작성으로 넘기기]를 눌렀습니다. 상담사가 직접 답장을 씁니다. |
| 처리 완료 | 승인, 수정하여 승인, 직접 작성 등록 중 하나로 끝났습니다. 어떤 방식인지는 작업 기록에서 봅니다. 끝난 뒤에도 [다시 수정]으로 최종 답장을 고칠 수 있습니다. |

### 0-3. 모든 기능에 해당하는 규칙

- 로그인하지 않으면 어떤 화면도 쓸 수 없습니다.
- 3명의 상담사는 **권한이 모두 같습니다.** 서로의 문의와 기록을 볼 수 있습니다.
- 사이트에는 **삭제 기능이 없습니다.** PRD에 없기 때문입니다. (문의, 초안, 기록, 위험 표현 모두 화면에서 지울 수 없습니다.)
- 화면의 안내 문구는 예시이며, 정확한 문장은 만들 때 정합니다.

### 0-4. 기능 목록

| 번호 | 기능 | PRD |
|---|---|---|
| A | 로그인 | 1장, 5장 |
| B | 문의 목록과 새 문의 입력 | 3장 "문의를 사이트에 넣는 방법" |
| F1 | 문의 자동 분류 | F1 |
| F2 | 근거가 붙은 답장 초안 | F2 |
| F3 | 위험 표현 경고 | F3 |
| F4 | 승인 흐름 | F4 |
| F5 | 작업 기록 | F5 |
| F6 | 성능 평가 (명령줄만, 화면 삭제) | F6 |
| F7 | 문의 현황 | F7 |
| F8 | CSV로 문의 여러 개 올리기 | F8 |
| F9 | 빠른 승인, 다음 문의 자동 이동, 비슷한 지난 문의 | F9 |
| F10 | 질문 - 최종 답변 쌍 (DB 보기) | F10 |

## 1. A. 로그인

### 1) 사용자가 입력하거나 누르는 것

| 항목 | 조건 |
|---|---|
| 아이디 | 필수. 미리 만들어 둔 3개 계정 중 하나: kim(김상담), park(박상담), lee(이상담) |
| 비밀번호 | 필수. 연습용 값(세 계정 모두 같음, `backend/README.md`에 적어 둠) |
| [로그인] 버튼 | 누르면 확인 |

### 2) 정상 처리

- 아이디와 비밀번호가 맞으면 상담 화면(메인)으로 이동합니다.
- 이후 상담사가 하는 모든 일(승인, 수정, 재작성, 직접 작성)에 이 상담사의 이름이 남습니다.
- 화면 위쪽에서 지금 로그인한 상담사가 누구인지 알 수 있습니다.

### 3) 잘못 입력하거나 실패할 때

- 아이디나 비밀번호가 비어 있으면 로그인되지 않고 입력하라는 안내가 나옵니다.
- 아이디나 비밀번호가 틀리면 로그인되지 않고, "아이디 또는 비밀번호가 맞지 않습니다" 같은 안내가 나옵니다. 어느 쪽이 틀렸는지는 알려주지 않습니다.
- 로그인하지 않은 채 다른 화면 주소로 들어가면 로그인 화면으로 돌아옵니다.
- 비밀번호를 여러 번 틀려도 계정을 막지 않습니다. 횟수 제한은 없습니다. (확정: Q10)
- 화면 위쪽에 [로그아웃] 버튼이 있고, 누르면 로그인 화면으로 돌아갑니다. 로그아웃하지 않아도 브라우저를 닫으면 로그인이 풀립니다. 그 외의 로그인 유지 시간 규칙은 두지 않습니다. (확정: Q10)

### 4) 누가 보거나 수정·삭제할 수 있는가

- 로그인 화면은 누구나 볼 수 있습니다.
- 회원 가입, 비밀번호 찾기, 비밀번호 변경은 **만들지 않습니다.** (PRD 6-1)
- 계정 3개는 프로젝트 작성자가 미리 만들어 두며, 화면에서 만들거나 지울 수 없습니다.

### 5) 제대로 만들었는지 확인하는 방법

1. 3개 계정 각각으로 로그인되는지 확인합니다.
2. 비밀번호를 틀리게 입력하면 로그인되지 않고 안내가 나오는지 확인합니다.
3. 아이디나 비밀번호를 비워 두고 눌러 봅니다.
4. 로그인 없이 상담 화면 주소로 들어가 로그인 화면으로 돌아오는지 확인합니다.
5. 로그인 후 작업을 하나 하고, 작업 기록에 그 상담사 이름이 남는지 확인합니다.
6. [로그아웃]을 누르면 로그인 화면으로 돌아가고, 다른 화면 주소로 들어가도 열리지 않는지 확인합니다.

## 2. B. 문의 목록과 새 문의 입력

### 1) 사용자가 입력하거나 누르는 것

**문의 목록 보기**
- 상담 화면 왼쪽에 **받은 문의** 목록이 보입니다. 문의를 누르면 오른쪽에 내용이 열립니다.
- 목록에서 각 문의의 상태(승인 대기 / 직접 작성 / 처리 완료)를 한눈에 볼 수 있습니다.
- 목록 위의 **상태 탭**(전체 / 승인 대기 / 빠른 승인 / 처리 완료)으로 골라 봅니다. 탭마다 건수가 있고, 처음에는 "전체"입니다. **"직접 작성" 탭은 없습니다.** 직접 작성 상태의 문의(초안을 만들지 못했거나 [직접 작성으로 넘기기]를 누른 문의)는 "승인 대기" 탭에 함께 보이고 목록의 상태 표시는 "직접 작성"입니다. (확정: 화면 디자인 수정 때 정렬 선택을 탭으로 바꿨고, 그 뒤 "직접 작성" 탭을 없애고 "빠른 승인" 탭을 넣음)
  - 어느 탭이든 최근에 들어온 문의가 위입니다. 해당하는 문의가 없는 탭은 "이 상태의 문의가 없습니다."를 보여 줍니다.
  - 탭을 바꿔도 지금 열어 본 문의는 그대로 열려 있습니다. 선택한 탭은 화면을 다시 열면 "전체"로 돌아갑니다.
- 목록과 문의 내용 사이의 **가운데 선을 끌어서** 목록 너비를 바꿀 수 있습니다 (처음 440px, 최소 280px, 최대 화면의 60%). 선에 포커스를 두고 좌우 화살표 키로도 바꿀 수 있고, 마지막으로 정한 너비는 이 브라우저에 기억해 둡니다.
- 날짜와 시각은 `2026.11.03 09:51 AM` 형태로 보여 줍니다(이 컴퓨터의 시각 기준).

**새 문의 입력** (시연용)

- 목록 아래 "새 문의 입력" 제목(▾)을 누르면 입력 칸이 부드럽게 **접히고 펼쳐집니다.** 위치는 그대로(목록 아래)이고, 처음에는 펼쳐져 있습니다. 접어 두면 목록이 그만큼 길어집니다. 접어도 쓰던 글은 남고, [CSV로 여러 개 올리기]는 계속 보입니다. 접힌 칸은 Tab 키로 닿지 않으며, 접어 둔 채 등록이 실패하면 안내가 보이도록 저절로 펼쳐집니다. 접은 상태는 화면을 다시 열면 펼침으로 돌아옵니다.

| 항목 | 조건 |
|---|---|
| 문의 내용 | 필수. 글을 쓰는 칸 하나뿐입니다. 구매자인지 판매자인지는 고르지 않습니다. 모델이 문장을 보고 판단합니다. |
| [등록] 버튼 | 누르면 문의가 들어갑니다. |

- 내용은 **최대 1,000자**입니다. 넘으면 등록되지 않고 글자 수 안내가 나옵니다. (확정: Q8)
- 미리 넣어 두는 가짜 문의는 **20개**입니다. 학습용·평가용 문의와는 따로 만든 것입니다. (확정: Q11)

### 2) 정상 처리

- 새 문의가 저장되어 목록에 나타납니다.
- 저장되는 순간 자동으로 분류(F1)가 시작되고, 모든 문의에 초안(F2)이 만들어져 승인 대기가 됩니다. 초안을 만들 수 없을 때만 직접 작성으로 넘어갑니다.
- 화면에서는 새 문의가 목록에 보이고, 곧 상태와 분류 결과가 채워집니다.

### 3) 잘못 입력하거나 실패할 때

- 내용이 비어 있으면(공백만 있는 경우 포함) 등록되지 않고 입력하라는 안내가 나옵니다.
- 분류가 오류로 실패해도 문의는 저장되고, 분류 결과 없이 정책 전체에서 근거를 찾아 초안을 만듭니다. 화면에 "문의 종류를 분류하지 못했습니다. 문의 내용을 직접 확인해 주세요."라고 알려줍니다.
- 초안 만들기가 오류로 실패하면 문의는 저장되고, 상태가 "직접 작성"이 됩니다. 화면에 "자동 처리에 실패해 직접 작성으로 넘어갔습니다"라고 알려줍니다. (확정: Q3, Phase 4 뒤 변경)

### 4) 누가 보거나 수정·삭제할 수 있는가

- 모든 상담사가 모든 문의를 볼 수 있고, 새 문의도 누구나 입력할 수 있습니다.
- 한 번 등록된 문의의 내용은 고칠 수 없고, 지울 수도 없습니다. (삭제·수정 기능이 PRD에 없음)
- 새 문의를 입력한 사실 자체는 작업 기록에 남지 않습니다. (PRD의 작업 기록은 승인·수정·재작성·직접 작성만 다룸)

### 5) 제대로 만들었는지 확인하는 방법

1. 로그인하면 미리 넣어 둔 문의가 목록에 보이는지 확인합니다.
2. 문의를 눌러 내용이 오른쪽에 열리는지 확인합니다.
3. 새 문의를 등록하면 목록에 나타나고, 분류 결과와 상태가 붙는지 확인합니다.
4. 빈 내용으로 등록해 막히는지 확인합니다.
5. 다른 상담사로 로그인해도 같은 문의가 보이는지 확인합니다.

## 3. F1. 문의 자동 분류

### 1) 사용자가 입력하거나 누르는 것

- 사용자가 따로 누르는 것은 없습니다. 문의가 등록되면 자동으로 일어납니다.
- 분류에 쓰이는 입력은 **문의 내용 글** 하나뿐입니다.

### 2) 정상 처리

- 문의가 아래 7가지 중 하나로 나뉩니다.

| 문의한 사람 | 종류 |
|---|---|
| 구매자 | 배송 / 검수 결과 / 취소·환불 / 결제 |
| 판매자 | 검수 불합격 / 페널티 / 정산 |

- **저장되는 것:** 분류된 종류, 확신도(%)
- **화면에 보이는 것:** 문의 옆에 "분류 결과: 취소·환불 (확신도 92%)"처럼 종류와 확신도가 함께 보입니다.
- 분류는 이 프로젝트에서 직접 학습시킨 모델이 합니다.
- 확신도에 따라 다음 단계가 갈립니다. (F4 참고)

### 3) 잘못 입력하거나 실패할 때

- 분류 결과가 틀릴 수 있습니다. 확신도가 기준값보다 낮은 문의도 초안은 만들지만, "분류 확신도가 기준값(70%)보다 낮습니다. 문의 종류가 맞는지 먼저 확인해 주세요." 경고를 함께 보여줍니다. 이때는 분류를 믿을 수 없으므로 규정 문서를 **정책 전체**에서 찾습니다. (확정: Phase 4 뒤 변경)
- 모델이 분류를 하지 못하는 오류가 나면 문의는 저장되고, 분류 결과와 확신도가 없다고 표시됩니다. 이때도 정책 전체에서 근거를 찾아 초안을 만듭니다. (확정: Q3, Phase 4 뒤 변경)

### 4) 누가 보거나 수정·삭제할 수 있는가

- 모든 상담사가 분류 결과와 확신도를 볼 수 있습니다.
- 상담사가 분류 결과를 **직접 바꾸는 기능은 없습니다.** (PRD에 없음)

### 5) 제대로 만들었는지 확인하는 방법

1. 배송 문의처럼 뚜렷한 문의를 넣으면 맞는 종류와 높은 확신도가 나오는지 확인합니다.
2. 애매한 문의를 넣으면 확신도가 낮게 나오고, 초안과 함께 "분류 확신도가 낮음" 경고가 뜨는지 확인합니다.
3. 구매자 문의와 판매자 문의를 각각 넣어 7개 종류 안에서 나오는지 확인합니다.
4. 종류와 확신도가 모든 문의 옆에 보이는지 확인합니다.
5. 전체 정확도는 F6(성능 평가, `python -m ml.evaluate`)로 확인합니다.

## 4. F2. 근거가 붙은 답장 초안

### 1) 사용자가 입력하거나 누르는 것

- 처음 초안은 자동으로 만들어집니다. 사용자가 누르는 것은 없습니다.
- 두 번째 초안은 상담사가 [재작성]을 눌러 받습니다. (F4 참고)
- 초안을 만들 때 쓰이는 입력은 **문의 내용 글**과 **규정 문서**입니다.

### 2) 정상 처리

- **모든 문의에 초안을 만듭니다.** 규정 문서에서 문의와 관련된 조항을 먼저 찾고, 찾은 조항을 바탕으로 초안이 만들어집니다. 초안은 OpenAI API가 씁니다.
- 초안이 말한 조항 번호가 실제 규정 문서에 있는지 프로그램이 다시 확인합니다.
- **저장되는 것:** 초안 내용, 규정 문서, 규정 문서에 없는 내용(한 줄, 없으면 비어 있음), 몇 번째 초안인지(첫 번째 / 재작성한 두 번째)
- **화면에 보이는 것:** 답장 초안과, 그 아래에 규정 문서 번호와 조항 원문. (예: "[RFD-03] 환불 시점과 수단 — 원문")
- 규정 문서가 모두 `[구버전]` 라벨(또는 `[구버전 포함]`)이면 근거 옆에 "구버전 기준이라 현재와 다를 수 있음" 경고가 보입니다. 이때 초안은 박스 크기·퍼센트 같은 구버전 수치를 단정해서 쓰지 않습니다. 초안은 그대로 만들어지고 승인 대기가 됩니다. (확정: 구버전 근거 처리)
- **"규정 문서에는 없음" 표시 (확정: Phase 4 뒤 변경, 빠른 승인 뒤 기준 변경):** 초안은 규정 문서에 없는 내용을 지어내지 않고 "확인 후 안내드리겠습니다"처럼 일반적으로만 씁니다. 화면의 **"규정 문서에는 없음"**(과 이유 한 줄)은 **초안이 참고한 규정 문서가 하나도 없을 때만** 규정 문서 자리에 뜹니다. 상담사에게만 보이고 고객에게는 가지 않습니다.
  - 규정 문서를 하나라도 참고한 초안: 참고한 규정 문서만 보입니다. 모델이 "이 부분(예: 내 주문의 출고 예정일)은 규정에 없다"고 적은 일부 메모는 DB에는 남기지만 화면에는 띄우지 않습니다.
  - 규정 문서를 하나도 참고하지 못한 초안: 규정 문서 자리에 "규정 문서에는 없음" + 이유만 보입니다.
- 초안은 상담사가 승인하기 전에는 고객에게 나가지 않습니다.

### 3) 잘못 입력하거나 실패할 때

- 문의와 관련된 규정 문서를 찾지 못해도 초안은 만듭니다. 이때 초안에는 정책 내용이 들어가지 않고, "규정 문서에는 없음"이 표시됩니다.
- 규정 문서는 두 단계로 찾습니다. 먼저 **분류된 문의 종류에 연결된 조항들**(규정 문서의 의도→조항 매핑표)로 후보를 좁히고(확신도가 기준값보다 낮거나 분류가 없으면 정책 전체가 후보), 그 안에서 문의와 내용이 **비슷한 조항을 최대 3개 후보**로 뽑습니다. 이 단계는 확실히 상관없는 조항만 걸러내는 낮은 기준입니다. 후보 중 **실제로 쓴 조항과 조항에 없는 내용은 초안을 쓰는 모델이 말하고**, 쓴 조항 번호는 프로그램이 다시 확인합니다. 유사도 기준값은 학습용·미리 넣은 문의와 정책에 없는 질문으로 정했고 평가용 문의는 쓰지 않습니다. (확정: Q4 + 근거 찾기, Phase 4 뒤 변경)
- 초안이 규정 문서에 **없는 조항 번호**, 또는 **초안을 쓸 때 제공하지 않은 조항 번호**를 하나라도 말하면, 그 초안은 쓰지 않고 문의를 "직접 작성"으로 보냅니다. 실제로 있는 번호만 근거로 인정합니다. 번호를 하나도 말하지 않은 초안은 허용하며 "규정 문서에는 없음"으로 표시합니다. (확정: Q4)
- 초안을 만드는 외부 서비스(OpenAI)가 응답하지 않거나 오류가 나면 문의는 "직접 작성"이 되고 실패했다는 안내가 나옵니다. (확정: Q3)

### 4) 누가 보거나 수정·삭제할 수 있는가

- 모든 상담사가 초안과 규정 문서를 볼 수 있습니다.
- 초안을 고치는 방법은 F4의 [수정]뿐입니다. 규정 문서는 상담사가 바꿀 수 없습니다.
- 규정 문서는 프로젝트 작성자가 텍스트 파일로 넣으며, 화면에서 고치거나 지울 수 없습니다.

### 5) 제대로 만들었는지 확인하는 방법

1. 환불 문의처럼 정책에 답이 있는 문의를 넣으면 초안과 규정 문서가 함께 나오는지 확인합니다.
2. 화면에 나온 규정 문서의 번호와 원문이 규정 문서와 똑같은지 비교합니다.
3. 규정 문서에 없는 내용의 문의를 넣으면 초안은 나오되 규정 문서 자리에 "규정 문서에는 없음"이 뜨고, 초안에 정책 내용이 지어져 있지 않은지 확인합니다. 일부만 있는 문의에서는 규정 문서만 뜨고 "규정 문서에는 없음"은 뜨지 않는지 확인합니다.
4. 일부러 없는 조항 번호를 초안이 말하게 해서(시험용) 걸러지는지 확인합니다.
5. 박스·정보택처럼 구버전 조항만 해당하는 문의에서 "구버전 기준" 경고가 뜨고, 초안에 구버전 수치가 단정되어 있지 않은지 확인합니다.
6. 확신도가 낮은 문의에서 초안과 "분류 확신도가 낮음" 경고가 함께 뜨는지 확인합니다.

## 5. F3. 위험 표현 경고

이 기능은 두 부분입니다. **(가) 초안에서 위험 표현 찾기**, **(나) 설정 화면에서 위험 표현 목록 관리**.

### 1) 사용자가 입력하거나 누르는 것

**(가) 경고 보기**
- 초안이 만들어지면 자동으로 검사합니다. 상담사가 [수정]이나 [직접 작성]에서 [저장]·[등록]을 누를 때도 쓴 글을 검사합니다.

**(나) 목록에 문구 추가 (설정 화면)**

| 항목 | 조건 |
|---|---|
| 새 위험 표현 | 필수. 글 한 줄. 예: "전액 보상해 드립니다" |
| [추가] 버튼 | 누르면 목록에 들어갑니다. |

- 설정 화면에서 지금 목록을 모두 볼 수 있습니다.
- 처음 목록은 Claude가 15~20개 정도 초안을 만들고 프로젝트 작성자가 검토해 확정합니다. (PRD U7)

### 2) 정상 처리

**(가)** 초안 안에 위험 표현이 있으면, 상담 화면의 초안 위에 **경고**가 뜨고 **해당 문장이 표시**됩니다. 위험 표현이 없으면 경고가 없습니다.
**(나)** 추가한 문구가 목록에 나타나고, 그 이후 검사부터 사용됩니다.

- **저장되는 것:** 위험 표현 목록(추가된 문구 포함)

### 3) 잘못 입력하거나 실패할 때

- (나)에서 빈 문구는 추가되지 않고 입력하라는 안내가 나옵니다.
- 경고가 떠도 승인은 막지 않습니다. 상담사가 해당 문장을 확인하고 그대로 [승인]하거나, [수정]으로 고쳐서 처리할 수 있습니다. (확정: Q1)
- 검사 대상은 AI가 만든 초안, 상담사가 [수정]으로 저장하려는 글, [직접 작성]으로 등록하려는 답장입니다. 어느 경우든 위험 표현이 있으면 저장하기 전에 경고와 해당 문장을 보여주고, 저장 자체는 막지 않습니다. (확정: Q2)

### 4) 누가 보거나 수정·삭제할 수 있는가

- 모든 상담사가 경고와 위험 표현 목록을 볼 수 있고, 문구를 추가할 수도 있습니다.
- 이미 있는 문구를 고치거나 지우는 기능은 PRD에 없어 **만들지 않습니다.** 추가만 가능합니다.

### 5) 제대로 만들었는지 확인하는 방법

1. 설정 화면에서 처음 목록(15~20개)이 보이는지 확인합니다.
2. 위험 표현이 들어간 초안(시험용)에서 경고가 뜨고 그 문장이 표시되는지 확인합니다.
3. 위험 표현이 없는 초안에는 경고가 없는지 확인합니다.
4. 새 문구를 추가한 뒤, 그 문구가 들어간 초안에서 경고가 뜨는지 확인합니다.
5. 빈 문구를 추가해 막히는지 확인합니다.

## 6. F4. 승인 흐름

### 6-1. 문의가 갈래로 나뉘는 방법 (자동)

| 구분 | 조건 | 결과 |
|---|---|---|
| 승인 대기 | 초안이 만들어졌다 (확신도가 낮거나 규정 문서가 없어도 경고·"규정 문서에는 없음" 표시와 함께 만든다) | 초안과 근거를 보여주고 상담사의 선택을 기다립니다. |
| 직접 작성 | 초안을 만들 수 없었다 (외부 서비스 오류, 없는 조항 번호 등) | 초안 없이 상담사가 직접 답장을 씁니다. (재작성 뒤 [직접 작성으로 넘기기]를 눌러도 이 상태가 됩니다.) |

### 6-2. [승인]

**1) 누르는 것:** 승인 대기 초안을 읽고 [승인] 버튼을 누릅니다.
**2) 정상 처리:** 문의가 "처리 완료"가 됩니다. 기록에 "승인", 상담사 이름, 시각이 남고 화면 목록에서 상태가 바뀝니다. 답장은 고객에게 실제로 나가지 않습니다.
**3) 실패:** 저장 중 오류가 나면 상태가 바뀌지 않고 다시 시도하라는 안내가 나옵니다. 위험 표현 경고가 있어도 승인할 수 있습니다. 두 상담사가 같은 문의를 동시에 처리하려 하면 **먼저 저장한 사람의 처리만 적용**되고, 나중에 누른 사람에게는 "다른 상담사가 이미 처리했습니다"라고 알려주며 최신 상태를 보여줍니다. 이 규칙은 승인·수정·재작성·직접 작성·다시 수정에 모두 똑같이 적용됩니다. (확정: Q7)
**4) 권한:** 로그인한 어떤 상담사든 승인할 수 있습니다. 승인을 되돌리거나 지우는 기능은 없습니다.
**5) 확인:** 승인 대기 문의에서 [승인]을 누르면 상태가 처리 완료로 바뀌고 기록에 남는지 확인합니다.

### 6-3. [수정]

**1) 입력하는 것:** 초안이 고칠 수 있는 글 칸으로 바뀌고, 상담사가 내용을 고친 뒤 [저장]을 누릅니다.

| 항목 | 조건 |
|---|---|
| 고친 답장 | 필수. 비어 있으면 저장되지 않습니다. |

**2) 정상 처리:** 고치고 저장하면 **바로 처리 완료**가 되고 "수정하여 승인"으로 기록됩니다. 기록에는 초안과 고친 최종 답장이 함께 남습니다.
**3) 실패:** 빈 내용이면 저장되지 않고 입력하라는 안내가 나옵니다. 고친 글에 위험 표현이 있으면 경고와 해당 문장이 보이지만 저장은 됩니다.
**4) 권한:** 로그인한 어떤 상담사든 수정할 수 있습니다. 처리가 끝난 뒤에 다시 고치려면 6-7의 [다시 수정]을 씁니다.
**5) 확인:** 초안을 고쳐 저장하면 처리 완료가 되고, 기록에 "수정하여 승인"과 초안·최종 답장이 남는지 확인합니다.

### 6-4. [재작성]

**1) 누르는 것:** 첫 번째 초안이 마음에 들지 않을 때 [재작성]을 누릅니다.
**2) 정상 처리:**
- 새 초안(두 번째)이 만들어져 화면의 초안이 바뀌고, 규정 문서와 위험 표현 검사도 새로 합니다.
- 재작성은 **문의당 1번만** 됩니다. 두 번째 초안에서는 [재작성] 대신 **[직접 작성으로 넘기기]** 버튼이 나타납니다.
- [직접 작성으로 넘기기]를 누르면 그 문의의 상태가 "직접 작성"이 됩니다.
- 두 번째 초안에서도 [승인]과 [수정]은 계속 쓸 수 있습니다.
- 기록에 "재작성"이 남고, 재작성 전의 첫 번째 초안과 새 초안이 함께 기록됩니다. (확정: Q12)
**3) 실패:** 재작성 중 외부 서비스 오류가 나면 첫 번째 초안을 그대로 두고, 다시 눌러 달라는 안내가 나옵니다. 이때는 재작성 횟수로 세지 않습니다. 새 초안이 없는 조항 번호를 말했을 때도 마찬가지로 첫 번째 초안을 그대로 두고 다시 눌러 달라고 안내합니다. (확정: Q4)
**4) 권한:** 로그인한 어떤 상담사든 누를 수 있고, 한 상담사가 재작성했는지는 상관없이 문의당 1번입니다.
**5) 확인:** 첫 초안에서 [재작성] → 새 초안이 나오고 [재작성] 버튼이 사라지며 [직접 작성으로 넘기기]가 보이는지 확인합니다. 그 버튼으로 직접 작성이 되는지도 확인합니다.

### 6-5. 직접 작성

**1) 입력하는 것:** "직접 작성" 상태의 문의를 열고 답장을 쓴 뒤 [등록]을 누릅니다.

| 항목 | 조건 |
|---|---|
| 답장 내용 | 필수. 초안이 없어서 처음부터 씁니다. 비어 있으면 등록되지 않습니다. |

**2) 정상 처리:** 등록하면 **처리 완료**가 되고 "직접 작성"으로 기록됩니다. 기록에 최종 답장이 남습니다. 고객에게 실제로 나가지는 않습니다.
**3) 실패:** 빈 내용이면 등록되지 않고 안내가 나옵니다. 위험 표현이 있으면 경고와 해당 문장이 보이지만 등록은 됩니다.
**4) 권한:** 어떤 상담사든 직접 작성할 수 있습니다.
**5) 확인:** 초안 만들기가 실패한 문의(또는 재작성 뒤 직접 작성으로 넘긴 문의)에서 직접 작성으로 가는지 확인하고, 답장을 등록하면 처리 완료가 되고 기록에 남는지 확인합니다.

### 6-6. 기준값 바꾸기 (설정 화면)

**1) 입력하는 것:** 설정 화면에서 기준값(%)을 고치고 [저장]을 누릅니다. 처음 값은 70%입니다.

| 항목 | 조건 |
|---|---|
| 기준값 | 필수. 50~95% 사이의 숫자 (확정: Q5) |

**2) 정상 처리:** 저장한 값이 새 기준값이 됩니다. **저장한 뒤 새로 들어오는 문의부터** 적용되고, 이미 분류된 문의의 경고는 바뀌지 않습니다. (확정: Q5)
**3) 실패:** 숫자가 아니거나 비어 있거나 50~95%를 벗어나면 저장되지 않고 안내가 나옵니다.
**4) 권한:** 로그인한 어떤 상담사든 바꿀 수 있습니다.
**5) 확인:** 기준값을 올리거나 내린 뒤 같은 문의를 새로 넣었을 때 "분류 확신도가 낮음" 경고가 기대대로 붙고 빠지는지 확인합니다(상태는 모두 승인 대기). 이미 있던 문의의 경고는 그대로인지도 확인합니다.

### 6-7. [다시 수정] (처리 완료 후)

**1) 입력하는 것:** "처리 완료" 문의를 열면 최종 답장 옆에 [다시 수정] 버튼이 있습니다. 누르면 최종 답장이 고칠 수 있는 글 칸으로 바뀌고, 고친 뒤 [저장]을 누릅니다.

| 항목 | 조건 |
|---|---|
| 고친 최종 답장 | 필수. 비어 있으면 저장되지 않습니다. |

**2) 정상 처리:**
- 문의 상태는 "처리 완료"로 **그대로**입니다. (승인 대기나 직접 작성으로 돌아가지 않습니다.)
- 고친 글이 새 최종 답장으로 저장되고, 기록에 "수정"이 **한 줄 새로 쌓입니다.** 예전 기록은 그대로 남습니다.
- 위험 표현 검사도 다른 [수정]과 똑같이 합니다. 경고가 있어도 저장은 됩니다.
- 답장은 고객에게 실제로 나가지 않습니다.
**3) 실패:** 빈 내용이면 저장되지 않고 안내가 나옵니다. 저장 중 오류가 나면 이전 최종 답장이 그대로 남습니다.
**4) 권한:** 로그인한 어떤 상담사든 할 수 있습니다. 처음 처리한 상담사가 아니어도 됩니다. (확정: Q6)
**5) 확인:** 처리 완료 문의에서 [다시 수정]으로 글을 고쳐 저장하면 상태는 처리 완료 그대로이고, 최종 답장이 바뀌며, 기록에 새 "수정" 줄이 추가되고 이전 기록이 지워지지 않는지 확인합니다.

## 7. F5. 작업 기록

### 1) 사용자가 입력하거나 누르는 것

- 기록은 상담사가 승인·수정·재작성·직접 작성을 할 때 **자동으로** 남습니다. 처리 완료 후 [다시 수정]을 하면 "수정"이 한 줄 더 남습니다.
- 작업 기록 화면에서는 아래 두 가지로 거를 수 있습니다 (선택 메뉴에서 고르며, 처음은 둘 다 "전체").

| 거르는 항목 | 고를 수 있는 것 |
|---|---|
| 상담사 | 전체 / 김상담 / 박상담 / 이상담 |
| 행동 | 전체 / 승인 / 수정 / 재작성 / 직접 작성 |

### 2) 정상 처리

- **저장되는 것:** 시간, 상담사, 문의, 행동, 초안, 최종 답장
- **화면에 보이는 것:** 위 항목이 목록으로 보이고, 거르면 해당 기록만 남습니다. 행동은 색이 다른 뱃지로 보이며 머리글 "행동"은 뱃지와 같은 위치에 맞춥니다.
- **[자세히]:** 초안, (재작성이면) 새 초안, 최종 답장이 **각각 따로 둥근 상자**에 담겨 구분됩니다(새 초안은 연한 보라, 최종 답장은 연한 초록 배경).
- 로그아웃했다가 다시 로그인해도 기록이 남아 있어 나중에 다시 볼 수 있습니다.

### 3) 잘못 입력하거나 실패할 때

- 조건에 맞는 기록이 없으면 "기록이 없습니다" 같은 안내가 나옵니다.
- 기록을 남기는 중 오류가 나면 해당 작업(승인 등)도 완료되지 않아야 합니다. 이때 안내는 만들 때 정합니다.

### 4) 누가 보거나 수정·삭제할 수 있는가

- 모든 상담사가 모든 상담사의 기록을 볼 수 있습니다.
- 기록은 화면에서 **고치거나 지울 수 없습니다.** (삭제·수정 기능이 PRD에 없음)

### 5) 제대로 만들었는지 확인하는 방법

1. 승인, 수정, 재작성, 직접 작성을 각각 한 번씩 하고, 기록 화면에 4건이 모두 남았는지 확인합니다.
2. 각 기록에 올바른 상담사 이름, 시간, 행동이 있는지 확인합니다.
3. 수정 기록에 초안과 최종 답장이 함께 있는지 확인합니다.
4. 상담사별, 행동별 필터가 제대로 걸리는지 확인합니다.
5. 다른 상담사로 로그인해서도 같은 기록이 보이는지 확인합니다.

## 8-2. F7. 문의 현황 (Phase 5 뒤에 추가, 사용자 요청)

언제 어떤 종류의 문의가 얼마나 들어왔는지, 초안과 처리가 어땠는지 봅니다. 상단 메뉴의 "문의 현황"(작업 기록과 설정 사이)에서 엽니다.

### 1) 사용자가 입력하거나 누르는 것
- 기간 탭: **오늘** / 최근 7일 / 최근 14일(처음 값) / 최근 30일 / **직접 지정**
- **직접 지정:** 탭을 누르면 아래에 작은 캘린더가 열립니다. **시작일을 누르고 종료일을 누르면** 그 기간을 불러오고 캘린더가 닫히며 탭에 기간(예: "11.01 ~ 11.04", 올해가 아니면 "25.12.30 ~ 26.01.02")이 보입니다. 같은 날을 두 번 누르면 그날 하루만 봅니다. 달은 ‹ › 로 옮기고, 오늘 이후 날짜와 시작일에서 90일을 넘는 날짜는 누를 수 없습니다. 종료일을 시작일보다 앞 날짜로 눌러도 앞뒤를 바로잡습니다. Esc나 바깥을 누르면 아무것도 고르지 않고 닫히며 보던 기간은 그대로입니다.
- [표로 보기] / [그래프로 보기]
- 그래프의 칸(날짜 또는 시간)에 마우스를 올리거나 키보드로 이동

### 2) 정상 처리
- 날짜와 시각은 **한국 시간** 기준이고, 선택한 기간에 **들어온 문의**만 셉니다. 문의가 없는 칸은 0건으로 채웁니다.
- **오늘** 탭은 0시~23시를 시간대별로 보여 줍니다(다른 탭은 날짜별). 이때 요약은 "가장 많이 들어온 시간", "시간당 평균(0시부터 지금까지)"이 됩니다. 직접 지정에서 **하루만** 고르면 그날을 같은 모양(시간대별)으로 보여 주고, 오늘이 아닌 날은 칸 이름에 날짜("2026.11.02 14시")가 붙고 시간당 평균은 24시간 기준입니다.
- **직접 지정한 기간(여러 날)**은 날짜별로 보여 주고, 하루 평균은 고른 날수로 나눕니다. 막대가 많아지면(36일 이상) 가로축 글자는 10칸마다 붙습니다. 서버가 알려 주는 한국 시간의 오늘(`today`)을 캘린더의 "오늘"로 씁니다.
- 요약 4개: 총 문의 / 가장 많은 종류(건수·비율) / 가장 많이 들어온 날(시간) — 같은 건수면 더 최근 칸 / 하루(시간당) 평균(문의 없는 칸 포함).
- **날짜별(시간대별) 문의 건수:** 칸마다 한 막대이고, 문의 종류(배송, 검수 결과, 취소·환불, 결제, 검수 불합격, 페널티, 정산)별로 색이 나뉜 쌓은 막대입니다. 색은 종류마다 정해져 있어 기간이나 건수가 바뀌어도 바뀌지 않습니다. 분류 결과가 없는 문의가 있으면 회색 "분류 없음"이 더해집니다. 칸에 마우스를 올리면 총 건수와 종류별 건수가 말풍선으로 나옵니다. 가로축 글자는 7일은 매일, 14일은 이틀, 30일은 닷새, 오늘은 3시간에 한 번이며 가장 최근 칸에는 항상 있습니다.
- **종류별 합계:** 건수가 많은 순서로 종류마다 색 표시, 건수, 비율.
- **규정 문서에는 없음 비율:** 초안이 규정 문서를 하나도 참고하지 못해 "규정 문서에는 없음"이 된 문의의 비율입니다. 초안이 있는 문의 중에서 **지금 초안(재작성했다면 새 초안)**이 참고한 규정 문서가 0개인 문의를 셉니다(일부만 없다는 메모는 세지 않음). 전체 비율, 종류별 가로 막대(높은 순), 날짜(시간)별 막대를 보여 줍니다. 높은 종류일수록 규정 문서를 더 보강해야 한다는 뜻입니다.
- **확신도가 낮은 문의 비율:** 분류 확신도가 지금의 기준값(설정 화면의 값)보다 낮거나 분류를 하지 못한 문의의 비율입니다. 전체, 종류별(높은 순), 날짜(시간)별로 보여 줍니다. 기준값과 같으면 낮은 것이 아닙니다.
- **처리 현황:** 이 기간에 들어온 문의의 지금 상태(승인 대기 / 직접 작성 / 처리 완료 건수), 처리 완료한 문의를 **마지막에 처리한 방법**(초안 그대로 승인 / 고쳐서 처리 / 직접 작성) 비율, 초안 그대로 승인한 비율, 재작성한 비율, 들어온 뒤 처리까지 걸린 시간(중앙값·평균)입니다.
- 비율은 나눌 대상이 없으면 0%가 아니라 "-"(값 없음)로 보여 줍니다.
- [표로 보기]를 누르면 모든 그래프가 표로 바뀝니다(건수는 날짜 × 종류 표, 비율은 종류별·날짜별 표).
- 미리 넣어 둔 가짜 문의와 직접 입력한 문의를 모두 셉니다. 종류는 분류 모델이 정한 결과입니다.

### 3) 잘못 입력하거나 실패할 때
- 기간이 오늘(1), 7, 14, 30이 아니면 "기간은 오늘, 7, 14, 30일 중에서 고르세요."로 거절합니다.
- 직접 지정(`start`, `end`)이 잘못되면 이유와 함께 거절합니다: 하나만 보냄("시작일과 종료일을 함께 지정하세요."), 날짜 형식이 틀림, 시작일이 종료일보다 늦음, 오늘 이후 날짜("오늘 이후의 날짜는 고를 수 없습니다."), 90일 초과("직접 지정은 최대 90일까지 고를 수 있습니다."). 화면이 막지 못한 경우에도 서버가 거절하고 이유를 화면에 보여 줍니다.
- 선택한 기간에 문의가 하나도 없으면 그래프 대신 "이 기간(…)에는 들어온 문의가 없습니다."를 보여 줍니다.
- 서버에 연결하지 못하면 안내 문구를 보여 줍니다.

### 4) 누가 보거나 수정·삭제할 수 있는가
- 로그인한 모든 상담사가 같은 숫자를 봅니다. 보기만 할 수 있고 수정·삭제는 없습니다.

### 5) 제대로 만들었는지 확인하는 방법
- 서버 시험: 날짜·시간대·종류별 건수, 한국 시간의 날짜 경계, 기간 경계, 분류 없음, 규정 문서에는 없음(최신 초안 기준, 참고한 규정 문서가 0개일 때만, 일부 없음 메모는 세지 않음, 초안 없는 문의는 제외), 확신도(기준값 경계·기준값 변경), 처리 방법(마지막 행동만), 재작성 비율, 처리 시간, 잘못된 기간, 로그인 필요.
- 화면 시험: 요약, 막대 설명, 고정 색, 말풍선, 기간·오늘 탭, 표로 보기, 비율 그래프, 처리 현황, 값 없음 표시, 오류. 직접 지정 캘린더(열기, 오늘 이후·90일 초과 날짜 비활성, 시작일→종료일 선택과 앞뒤 바로잡기, 하루만 고르기, 칠해진 기간, Esc·바깥 닫기, 다른 탭으로 돌아오기, 서버 거절 안내, 연도 표시).
- 서버 시험(직접 지정): 고른 날만 세기(양 끝 포함, 문의 없는 날 0건), days 무시, 하루는 시간대별(지난 하루는 24시간), 같은 날수의 최근 며칠과 숫자가 같음, 90일 경계(90일 되고 91일 안 됨), 잘못된 기간 8가지와 이유, 로그인 필요.

## 8-3. F8. CSV로 문의 여러 개 올리기 (Phase 5 뒤에 추가, 사용자 요청)

상담 화면 왼쪽 "새 문의 입력" 옆의 **[CSV로 여러 개 올리기]**로 문의 여러 개를 한 번에 등록합니다. 서버는 바꾸지 않았고, 화면이 문의를 **하나씩 차례로** 기존 등록(분류 + 초안 만들기)에 보냅니다.

### 1) 사용자가 입력하거나 누르는 것
- CSV 파일 한 개 선택 (예시 파일을 받을 수 있음). 파일에서 찾은 문의 개수와 처음 5개를 보여 주고, [N개 등록 시작]을 눌러야 등록합니다.
- 진행 중에는 [중단]을 누를 수 있습니다.

### 2) 정상 처리
- **파일 형식:** 한 줄에 문의 하나, 첫 번째 칸을 씁니다. 첫 줄이 머리글(문의, 문의 내용, 내용, 질문, text, body ...)이면 그 이름의 칸을 씁니다. 따옴표로 감싼 칸 안의 쉼표·줄바꿈은 문의 내용으로 지킵니다. UTF-8과 엑셀 한국어 CSV(EUC-KR)를 모두 읽습니다.
- **제한:** 한 번에 30개, 문의 하나는 1,000자, 파일은 1MB까지. 빈 줄은 건너뜁니다(개수를 알려 줌).
- **진행 상황:** "3 / 20 번째 문의를 분류하고 초안을 만드는 중... (성공 2, 실패 0)"과 진행 막대. 문의 하나가 끝날 때마다 받은 문의 목록이 갱신됩니다. 문의 하나에 몇 초가 걸리고 개수만큼 OpenAI 비용이 듭니다(안내문에 적어 둠).
- **일부가 실패하면 실패한 것만 빼고 다음 문의를 이어서** 등록합니다. 끝나면 "18개 등록 · 2개 실패"와 실패한 문의(몇 번째 줄, 내용, 이유)를 보여 줍니다.
- 1,000자가 넘는 문의는 서버에 보내지 않고 실패로 적습니다.

### 3) 잘못 입력하거나 실패할 때
- 31개 이상: "한 번에 30개까지 올릴 수 있습니다. 이 파일에는 N개가 있습니다. 나눠서 올려 주세요." (아무것도 등록하지 않음)
- 문의가 없는 파일: "문의를 찾지 못했습니다..." / 너무 큰 파일: "파일이 너무 큽니다..."
- 서버에 연결할 수 없거나 로그인이 풀리면 다음 문의도 실패하므로 **그때만 멈추고**, 나머지는 "등록하지 않음"으로 알립니다.
- 중단하면 지금 처리 중인 문의까지만 하고 멈춥니다.

### 4) 누가 보거나 수정·삭제할 수 있는가
- 로그인한 모든 상담사가 쓸 수 있습니다. 올린 문의는 직접 입력한 문의와 같습니다(작성자 표시, 이후 처리·기록 모두 동일).

### 5) 제대로 만들었는지 확인하는 방법
- 화면 시험: 순서대로 등록, 일부 실패 후 계속, 1,000자 초과, 연결 끊김·로그인 풀림에서 멈춤, 중단, 진행 숫자, 31개 초과·0개·큰 파일, 따옴표·여러 줄 칸, 다른 파일 다시 고르기. CSV 읽기(EUC-KR, 따옴표, 머리글) 시험.
- 실제 브라우저와 실제 서버·OpenAI로 3줄(1줄은 1,000자 초과) 파일을 올려 2개 등록·1개 실패를 확인하고, 시험으로 만든 문의는 지웠습니다.

## 8-4. F9. 빠른 승인, 다음 문의 자동 이동, 비슷한 지난 문의 (Phase 5 뒤에 추가, 사용자 요청)

상담사가 같은 일을 덜 반복하도록 상담 화면에 세 가지를 더했습니다. 승인 흐름(6장)의 규칙(승인해야 처리 완료, 작업 기록, 동시 처리 보호)은 그대로 지킵니다.

### 1) 사용자가 입력하거나 누르는 것
- **빠른 승인 탭**을 누르면 빠른 승인 가능한 문의만 보입니다 (탭은 전체 / 승인 대기 / 빠른 승인 / 처리 완료).
- 빠른 승인 탭에서 목록 오른쪽 위(정렬 옆)의 **[일괄 승인]**을 누르면 확인 창이 뜨고, [N건 일괄 승인]을 눌러야 승인됩니다.
- 기존 [승인], [수정]의 [저장], 직접 작성의 [등록]을 누르면 처리 뒤 자동으로 다음 문의가 열립니다.
- [수정]이나 [다시 수정]을 누르거나, 직접 작성 문의를 열면 "비슷한 지난 문의"가 나옵니다.

### 2) 정상 처리
- **빠른 승인 가능 기준 (3가지 모두, 서버가 한 곳에서 계산):** 승인 대기 문의의 지금 초안이 ① 분류 확신도가 **90%를 넘고**(설정 화면의 기준값과 별개의 고정값) ② 참고한 규정 문서가 **하나라도 있고**("규정 문서에는 없음"이 아님) ③ **위험 표현 경고가 없을 때**. 재작성한 초안도 같은 기준입니다.
- 가능한 문의는 목록에서 노란 "승인 대기" 표시 옆에 검은 **"빠른 승인"** 표시가 붙습니다(어느 탭에서나). 승인 대기 문의 처리 상태가 바뀌거나 위험 표현을 추가하면 다음에 목록을 불러올 때 표시가 사라집니다.
- **[일괄 승인]:** 빠른 승인 탭의 문의 전부(번호와 version)를 서버에 보냅니다. 서버는 문의마다 ① 상담사가 본 version이 지금과 같은지 ② 아직 승인 대기인지 ③ 빠른 승인 기준을 아직 만족하는지 다시 확인하고, 모두 맞으면 초안 그대로 승인합니다(처리자는 누른 상담사, 작업 기록에는 [승인]을 누른 것과 똑같이 "승인"이 한 줄씩 남음). 하나가 안 돼도 나머지는 승인됩니다. 끝나면 "N건 승인했습니다"와, 건너뛴 문의의 번호·이유를 보여 줍니다. 목록과 열려 있던 문의는 새로 불러옵니다.
- **다음 문의로 자동 이동:** 승인(빠른 승인 목록에서의 [승인] 포함), 승인 대기 문의의 [수정] 저장, 직접 작성 [등록]이 끝나면, **지금 보이는 목록(탭·정렬 그대로)**에서 아래쪽의 아직 처리하지 않은(승인 대기 또는 직접 작성) 문의를 엽니다. 아래에 없으면 위쪽에서 가장 가까운 것, 둘 다 없으면 그 문의에 머뭅니다. 화면에는 "승인했습니다. 다음 문의 #N로 이동했습니다."라고 알립니다. 처리 완료 문의의 [다시 수정]은 이동하지 않습니다. 새 문의를 열면 내용 칸은 맨 위부터 보입니다.
- **비슷한 지난 문의:** 처리 완료된 문의(지금 문의 제외) 중 뜻이 비슷한 것을 비슷한 순으로 **최대 3개**, 비슷한 정도가 **45% 이상**인 것만 보여 줍니다. 문의 종류, 번호, 비슷한 정도, 처리한 시각, 문의 내용, 최종 답장이 나오고 가장 비슷한 문의의 답장만 펼쳐져 있습니다. 참고용이며 답장 칸에 자동으로 넣지 않습니다. 규정 문서 찾기와 같은 임베딩(`text-embedding-3-large`)을 쓰고, 안 되면 글자 조각(TF-IDF, 15% 이상)으로 찾습니다. 문의의 벡터는 파일에 저장하지 않고 서버 메모리에만 둡니다. 45%/15%는 실제 문의 43건(903쌍)의 점수로 정했습니다(다른 종류끼리 3.5%만 걸림).

### 3) 잘못 입력하거나 실패할 때
- 빠른 승인 가능한 문의가 없으면 "빠른 승인할 수 있는 문의가 없습니다."를 보여 주고 [일괄 승인] 버튼은 누를 수 없습니다.
- 승인 요청 자체가 실패하면(서버 연결 등) 확인 창에 이유를 보여 주고 다시 누를 수 있습니다.
- 서버가 건너뛰는 이유: "다른 상담사가 이미 처리했습니다. 최신 상태를 불러왔습니다."(version이 달라짐), "이미 처리된 문의입니다.", "빠른 승인 조건을 더 이상 만족하지 않습니다.". 화면이 이상한 문의를 보내도 서버가 기준을 다시 확인하므로 기준 밖의 문의는 승인되지 않습니다.
- 자동 이동 중 승인이 충돌(다른 상담사가 먼저 처리)이면 넘어가지 않고 최신 상태와 안내를 보여 줍니다.
- 비슷한 문의를 못 불러오면 "비슷한 문의를 불러오지 못했습니다. 답장은 그대로 쓸 수 있습니다."라고만 알리고 답장 쓰기는 막지 않습니다. 비슷한 문의가 없으면 "비슷한 지난 문의가 없습니다."

### 4) 누가 보거나 수정·삭제할 수 있는가
- 로그인한 모든 상담사가 쓸 수 있습니다. 빠른 승인한 문의도 승인 대기 문의를 승인한 것과 똑같이 처리되어 [다시 수정]으로 고칠 수 있습니다.
- 승인해도 답장은 고객에게 실제로 발송되지 않습니다(확인 창에도 적어 둠).

### 5) 제대로 만들었는지 확인하는 방법
- 서버 시험: 빠른 승인 기준 각각(확신도 90% 경계·설정 기준값과 무관, 규정 문서 0개, 일부 없음 메모, 위험 표현, 처리 완료·직접 작성 제외, 분류 없음, 최신 초안 기준), [일괄 승인](전체 승인, 작업 기록, 조건이 달라진 문의·이미 처리된 문의·version이 다른 문의 건너뛰고 계속, 기준 밖 문의를 화면이 보내도 거절, 빈 요청, 로그인), 비슷한 지난 문의(가까운 순, 자기 자신·미처리 제외, 최대 3개, 기준 미만, 임베딩과 TF-IDF 대체, 없는 문의, 로그인).
- 화면 시험: 탭 구성(직접 작성 탭과 마우스 메뉴가 없음), 승인 대기 탭에 직접 작성 문의 포함과 건수, 빠른 승인 탭, "빠른 승인" 표시, [일괄 승인]의 확인·취소·결과·건너뜀·실패 후 다시, 자동 이동(아래→위→머묾, 처리 완료 건너뜀, 직접 작성, 수정 저장, 다시 수정은 안 움직임, 충돌), 비슷한 지난 문의(수정 눌렀을 때만, 취소, 찾는 중, 없음, 실패, 다시 수정, 직접 작성).
- 일부러 코드를 틀리게 해 보는 점검(서버 10가지, 화면 14가지)을 모두 시험이 잡아냈습니다.
- 실제 브라우저·서버·OpenAI로 확인하고 시험으로 만든 문의 4개(작업 기록 포함)는 지웠습니다 (당시의 승인 대기 탭 메뉴 화면 기준이며, 지금은 빠른 승인 탭으로 바뀜): 승인 대기 탭 메뉴(탭에서 메뉴로 마우스를 옮겨도 닫히지 않음), 빠른 승인 목록 16건과 확인 창(취소), 승인하면 109 → 108 → 107로 자동 이동, 서버 빠른 승인에 106(가능)·107(확신도 84.1%)·108(이미 처리)을 보내 106만 승인, 비슷한 지난 문의 82~85%로 3건.

## 8-5. F10. 질문 - 최종 답변 쌍 (DB 보기, 빠른 승인 뒤에 추가, 사용자 요청)

상담사가 문의를 처리하면(승인·수정·직접 작성) 그 **질문과 최종 답장이 "쌍"으로** DB에서 조회됩니다. 화면은 없고 DB의 **보기(view) `qa_pairs`**입니다. 지금은 **저장만** 합니다(화면, AI 초안, 분류 모델 학습에는 쓰지 않습니다).

### 1) 사용자가 입력하거나 누르는 것
- 없습니다. 기존 [승인], [수정]의 [저장], 직접 작성의 [등록], [다시 수정]의 결과가 그대로 쌍이 됩니다. 쌍은 DB 관리 화면(Supabase)이나 SQL(`SELECT * FROM qa_pairs`)로 봅니다.

### 2) 정상 처리
- **대상: 처리 완료 전부.** 승인 대기·직접 작성 상태(아직 답장이 없는 문의)는 나오지 않습니다.
- **복사본 표가 아니라 보기입니다.** `inquiries`의 처리 완료 줄을 쌍으로 보여 줄 뿐이라 항상 최신이고, 같은 글이 두 곳에 있지 않아 따로 갱신할 일이 없습니다. 문의 하나는 쌍 한 줄입니다(승인 뒤 여러 번 고쳐도 줄이 늘지 않음).
- **칸:** `inquiry_id`(문의 번호), `question`(질문), `answer`(지금의 최종 답장), `predicted_label`·`confidence`(분류 종류와 확신도), `resolution`(**처리 방법**: `approve` 초안 그대로 승인 / `edit` 고쳐서 / `manual_write` 직접 작성), `rewrite_count`(재작성 횟수), `answered_by`·`answered_at`(지금 답장을 마지막으로 저장한 상담사와 시각), `asked_at`(문의가 들어온 시각), `source`(`seed` 미리 넣은 문의 / `user` 직접 넣은 문의).
- **[다시 수정]하면** 같은 줄의 `answer`가 새 글로 바뀌고 `resolution`은 `edit`, `answered_by`는 마지막으로 고친 상담사가 됩니다. (고친 이력은 작업 기록 `action_logs`에 그대로 쌓입니다.)

### 3) 잘못 입력하거나 실패할 때
- 해당 없음(입력이 없고 보기만 합니다). 승인 대기·직접 작성 문의는 쌍에 나타나지 않습니다.

### 4) 누가 보거나 수정·삭제할 수 있는가
- 서버가 쓰는 DB 계정과 DB 관리자만 읽을 수 있습니다. 보기는 기본적으로 표의 접근 제한(RLS)을 우회할 수 있어서, `security_invoker`로 보는 사람의 권한을 따르게 하고 Supabase가 외부에 열어 두는 역할(`anon`, `authenticated`)의 권한은 회수했습니다. 화면에서 지우거나 고치는 기능은 없습니다.

### 5) 제대로 만들었는지 확인하는 방법
- 서버 시험(`tests/test_qa_pairs.py` 9개): 승인·수정·직접 작성이 각각 쌍이 되고 처리 방법이 맞음, 재작성 뒤 승인은 두 번째 초안이 답장, 처리 안 된 문의는 제외, [다시 수정]해도 줄이 늘지 않고 마지막 상담사가 표시됨, 쌍이 항상 원래 문의와 같음, RLS 우회 방지(`security_invoker`, Supabase와 같은 자동 권한 조건에서도 외부 역할이 못 읽음).
- 일부러 SQL을 틀리게 해 본 점검 6가지(`security_invoker` 빼기, 권한 회수 빼기 2가지, 처음 행동 쓰기, 처리 안 된 문의 포함, 처음 상담사 쓰기)를 모두 시험이 잡아냈습니다.

### Phase 4 뒤에 바뀐 결정 (확정)

Phase 4까지 만든 뒤 사용자가 요청해서 바꾼 두 가지입니다. 위 본문에 모두 반영했습니다.

1. **받은편지함 정렬:** 상태별로 모아보기(처음 값) / 최신순 / 오래된순을 고를 수 있습니다. → 이후 화면 디자인 수정 때 **상태 탭**으로 바뀌었습니다 (위 1장 참고).
2. **모든 문의에 초안:** "직접 작성"이 너무 많아 상담사를 돕는다고 보기 어려워서, 확신도가 낮거나 규정 문서가 없는 문의에도 초안을 만듭니다.
   - 규정 문서 안의 내용은 지금처럼 규정 문서와 함께 보여주고, 조항에 없는 내용은 초안이 그 부분을 일반적으로만 씁니다. "규정 문서에는 없음" 표시는 처음에는 일부만 없을 때도 띄웠지만 **참고한 규정 문서가 하나도 없을 때만** 띄우는 것으로 바뀌었습니다 (아래 "빠른 승인 뒤 바뀐 결정").
   - 확신도가 기준값보다 낮으면 초안과 함께 경고를 띄우고, 규정 문서는 정책 전체에서 찾습니다. 기준값은 이 경고를 띄우는 기준이 됩니다.
   - "직접 작성" 상태는 초안 만들기가 실패했을 때와 재작성 뒤 넘기기를 눌렀을 때만 남습니다.

### 화면 수정 뒤 바뀐 결정 (확정)

1. 새 문의 입력칸에서 **Enter는 등록, Shift+Enter는 줄바꿈**입니다. 한글을 입력하는 중(글자 조합 중)에 누른 Enter는 등록하지 않습니다.
2. 받은 문의 목록에 **정렬(최신순 / 오래된순)** 선택을 추가했습니다. 상태 탭과 함께 쓰이고 처음 값은 최신순입니다.
3. 글자 크기를 전체적으로 1px씩 키우고 "받은 문의"·"문의 #번호" 제목은 더 크게 했습니다.
4. 상단 메뉴에 "문의 현황"을 추가했습니다 (8-2장). 이어서 오늘 탭(시간대별), 규정 문서에는 없음 비율, 확신도가 낮은 문의 비율, 처리 현황을 더했습니다.
5. 왼쪽 위 **"CSFlow"는 누르면 상담 화면으로 이동하는 버튼**입니다.
6. 메뉴의 선택 표시(알약)가 선택한 메뉴로 부드럽게 미끄러져 옮겨 갑니다. 받은 문의의 상태 탭(전체·승인 대기·빠른 승인·처리 완료)과 문의 현황의 기간 탭(오늘·최근 7·14·30일)도 같은 방식입니다. 처음 열 때나 창·목록 너비를 바꿀 때는 움직임 없이 제자리를 잡고, 탭을 눌러 바꿀 때만 움직입니다.
7. **승인·수정·재작성 버튼은 내용 맨 아래에 있고, 그 자리가 화면 밖일 때만** 내용 칸 바로 아래에 같은 버튼이 나타납니다. 아래 버튼은 내용 칸 밖에 있어 글씨를 덮지 않습니다. 수정 중에는 나타나지 않습니다.
8. **답장 초안은 문단으로 나눠서** 씁니다(문단 3~4개, 문단 사이 빈 줄 한 줄, 마지막 문단은 마무리 인사 한 줄). 이미 만들어 둔 예전 초안은 그대로입니다.
9. **분류 확신도 낮음 경고 상자는 살짝 붉은색**(옅은 붉은 배경, 붉은 테두리, 짙은 붉은 글자)입니다. 같은 자리에 나오는 다른 자동 안내(분류 실패, 자동 처리 실패)도 같은 색입니다. 이전에는 회색이라 경고처럼 보이지 않았습니다.
10. **문의 현황에 "직접 지정"** 기간 탭을 추가했습니다: 작은 캘린더에서 시작일과 종료일을 골라 최대 90일까지 봅니다 (8-2장).
11. **승인 대기 ↔ 빠른 승인 탭을 오가도 요소가 움직이지 않습니다.** 빠른 승인 탭에서만 생기는 [일괄 승인](당시 이름 [빠른 승인]) 버튼이 목록 위 제목 줄을 2.4px 키워 아래의 탭과 목록이 밀리던 것을, 제목 줄 높이를 고정해 막았습니다(실제 브라우저에서 모든 보기의 위치가 같음을 확인). 목록의 스크롤바가 생기고 없어져도 글이 옆으로 밀리지 않게 자리를 비워 둡니다.
12. **선택 메뉴를 캘린더 창과 같은 모양으로 바꿨습니다.** 받은 문의의 정렬(최신순 / 오래된순)과 작업 기록의 상담사·행동 선택이 브라우저 기본 선택 상자라 딱딱해 보여서, 둥근 흰 상자 + 그림자 + 같은 글꼴의 메뉴(`SelectMenu`)로 바꿨습니다. 지금 고른 항목에 체크 표시가 있고, 단추의 ˅ 표시는 열리면 뒤집힙니다. 키보드로도 쓸 수 있습니다(↑ ↓ Home End로 옮기고 Enter로 고름, Esc는 고르지 않고 닫음, Tab으로 나가면 닫힘). 바깥을 눌러도 닫힙니다.
13. **작업 기록 표의 글자가 꺾이지 않습니다.** 긴 문의 칸이 다른 칸을 눌러 상담사 칸의 "이상담"과 [자세히]가 두 줄로 갈라지던 것을, 시간·상담사·행동·자세히 칸은 줄바꿈을 막아 고쳤습니다. 긴 글은 문의 칸에서만 줄바꿈됩니다.
14. **받은 문의의 탭을 "전체 / 승인 대기 / 빠른 승인 / 처리 완료"로 바꿨습니다.** "직접 작성" 탭을 없애고 그 자리에 빠른 승인 탭을 넣었습니다(승인 대기 탭에 마우스를 올리면 뜨던 메뉴는 없앰). 모든 문의에 초안이 만들어지고 수정할 수 있으므로 "직접 작성" 탭이 따로 필요 없다는 판단입니다. 초안을 만들지 못했거나 직접 작성으로 넘긴 문의는 아주 드물게 생기며, 사라지지 않도록 **승인 대기 탭에 함께** 보이게 했습니다(상태 표시는 "직접 작성" 그대로). 작업 기록의 행동 필터에서도 "직접 작성"을 뺐습니다(직접 작성한 기록은 "전체"에서 계속 보임).
15. **빠른 승인 탭의 버튼 이름을 [일괄 승인]으로 바꿨습니다.** 확인 창 제목과 단추도 "일괄 승인", "N건 일괄 승인"입니다. 동작은 같습니다(그 탭의 문의 전부를 초안 그대로 승인, 서버가 문의마다 조건을 다시 확인).

### 규정 문서 보강 뒤 바뀐 결정 (확정)

1. **용어:** 사용자에게 보이는 "근거 조항"을 **"규정 문서"**로 바꿉니다 (예: "규정 문서에는 없음"). 조항 ID(PEN-06 등)는 그대로입니다.
2. **규정 문서 102개 조항:** 공개 서비스 안내를 바탕으로 이름·주소·전화번호·브랜드명을 지워 요약해서 다시 썼고, 기존 47개 ID는 유지했습니다. 가상 조항은 4개입니다.
3. **조항 형식:** `- 이런 문의에 쓰임:` 줄(고객 말투 예시)을 추가했습니다. 규정 문서를 찾는 글자 비교에만 쓰이고 화면 원문과 초안 재료에는 나오지 않습니다.
4. **초안 지침:** 해당 조항 모두 반영, 이용 경로·수치 구체 안내, 공감 → 결론 → 안내 → 다음 행동 → 마무리 순서, 필요한 정보가 없으면 요청.
5. **규정 문서 찾는 방식:** 정답 표로 TF-IDF / 임베딩 / 섞기를 비교해 **임베딩(`text-embedding-3-large`, 뜻 비교)**으로 바꿨습니다 (3등 안 정확도 79.1% → 88.1%, 예시 줄 없이 66.4% → 81.3%). 분류된 종류의 후보 조항 안에서 문의와 뜻이 가장 가까운 3개를 고르는 흐름은 그대로입니다.
6. **임베딩이 안 될 때:** OpenAI 키가 없거나 임베딩 호출이 실패하면 그 순간만 TF-IDF로 찾고 상담 흐름은 멈추지 않습니다. 고객 문의의 임베딩은 파일에 저장하지 않습니다.

### 빠른 승인 뒤 바뀐 결정 (확정)

1. **"규정 문서에는 없음" 표시 기준 변경:** 참고한 규정 문서가 **하나라도 있으면 표시하지 않고, 하나도 없을 때만** 표시합니다. 모델이 적은 "일부만 규정에 없다"는 메모(예: 내 주문의 출고 예정일)는 화면에 띄우지 않기로 했습니다(DB에는 남음). 문의 현황의 "규정 문서에는 없음 비율"도 같은 기준입니다. 실제 DB의 문의 43건에서 화면에 이 문구가 뜨던 38건이 8건으로 줄었습니다. *알아 둘 점: 일부 메모가 보이지 않으므로 초안 안에 "확인 후 안내드리겠습니다"처럼 상담사가 따로 확인해야 하는 약속이 있어도 표시가 없습니다. 이 때문에 빠른 승인으로 나간 초안에도 그런 문장이 있을 수 있습니다.*
2. **빠른 승인과 일괄 승인:** (처음에는 승인 대기 탭에 마우스를 올려 고르는 메뉴였다가 별도 **빠른 승인 탭**이 되었고, 버튼 이름은 [빠른 승인]에서 **[일괄 승인]**이 되었습니다.) 빠른 승인 탭 오른쪽 위의 [일괄 승인] 한 번으로 그 탭의 문의 전부를 초안 그대로 승인합니다. 기준은 확신도 90% 초과 + 규정 문서 참고 + 위험 표현 없음입니다. 여러 건이 한꺼번에 승인되므로 누르면 먼저 확인 창을 띄웁니다(제가 더한 안전장치).
3. **자동 이동 범위:** 승인, 수정 저장, 직접 작성 저장 모두. ([다시 수정]은 제외 — 이미 처리한 문의를 고친 것이라 그 자리에 머무는 것이 자연스러워서 제가 정함.)
4. **비슷한 지난 문의:** 처음에는 보여 주지 않고 수정(다시 수정, 직접 작성 포함)을 눌렀을 때만 보여 줍니다.
